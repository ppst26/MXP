# Design: MaxPay P4a — สร้าง payout และกันเงิน

วันที่: 2026-08-29
สถานะ: อนุมัติ (design), รอตรวจ spec

> **คำแปล** — ฉบับภาษาอังกฤษที่ `2026-08-29-maxpay-p4a-payout-create-design.md`
> เป็นฉบับที่ยึดถือ และเป็นฉบับที่ implementer อ่าน ถ้าสองฉบับไม่ตรงกัน
> ให้ถือฉบับภาษาอังกฤษ ชื่อตาราง ชื่อคอลัมน์ ชื่อฟังก์ชัน คีย์ config
> และ SQL คงไว้เป็นภาษาอังกฤษตามมาตรฐานของโปรเจ็ค

## 1. เป้าหมาย

ให้ merchant สั่งจ่ายเงินให้ใครสักคนได้ ตัดเงินออกจากยอดที่ใช้ได้ของเขาทันทีที่เรา
รับคำสั่ง แล้วคืน reference ให้เขาไปเช็คสถานะ — **โดยเฟสนี้ไม่คุยกับธนาคารเลยแม้แต่
ครั้งเดียว**

P2b สร้างการลงบัญชีของ payout ไว้ครบแล้วทั้ง `PostPayoutCreated`,
`PostPayoutCompleted`, `PostPayoutFailed` แล้วทิ้งไว้โดยไม่มีใครเรียก เฟสนี้คือคน
เรียกตัวแรก P4b เป็นคนส่งเงินจริง P4c ปิดวงจรด้วย webhook และการให้คนตัดสิน

ที่แบ่งแบบนี้เพราะทุกอย่างใน P4a **ทดสอบได้เต็มที่กับฐานข้อมูลจริงโดยไม่มีความเสี่ยง
กับบัญชีธนาคารเลย** ถ้าดีไซน์ผิดจะเจอตั้งแต่ก่อนเงินขยับสักสตางค์

เอกสารอ้างอิงคือ PRD ใน `../MaxPay` โดยเฉพาะ `payout/CreatePayout.md`
(ฟิลด์ request/response), `payout/Payout.md` (วงจรสถานะและรูปแบบการอนุมัติ)
และไฟล์ของสอง endpoint สำหรับอ่าน

## 2. ขอบเขต

**อยู่ในเฟสนี้**

- `POST /api/v1/payout/create` — มี signature, idempotent
- ตาราง `payouts` และวงจรสถานะ
- กันเงิน **ยอด + ค่าธรรมเนียม** ผ่าน `PostPayoutCreated`
- guard ยอดเงินไม่พอ ที่ P2b ประกาศไว้แล้วไม่ได้สร้าง
- เก็บ `reserved_fee` ซึ่ง P2b เขียนคอมเมนต์ขอไว้ตรงๆ
- เลือกบัญชีต้นทางจาก config
- `GET /api/v1/payout/:reference_id` และ `GET /api/v1/payouts`

**ไม่อยู่ในเฟสนี้** — เขียนไว้ชัดเพื่อไม่ให้ใครเผลอทำ

- **ไม่มีการเรียกธนาคารใดๆ ทั้งสิ้น** ไม่สร้าง transfer order ไม่เช็คชื่อ ไม่ใช้ PIN
  service `transfer` ไม่ถูกต่อเข้ามาในเฟสนี้เลย
- worker ที่กวาดแถว `PENDING` (P4b)
- `PostPayoutCompleted` / `PostPayoutFailed` (P4b)
- webhook ทุกชนิด (P4c)
- reconciler, การถอยไปดู statement และ `NEEDS_REVIEW` (P4c)
- payout แบบ bulk — endpoint ของ PRD รับผู้รับคนเดียว และโหมด bulk ของ rail
  ไม่ถูกใช้
- buffer สภาพคล่องและ auto-sweep — ยังไม่มีบัญชี `OUTBOUND` ให้วัด และ
  `pool.balance_refresh_enabled` ยังไม่เคยรันจริง **guard ที่อ่านตัวเลขเก่าค้าง
  แย่กว่าไม่มี guard เพราะคนเชื่อมัน**

## 3. ข้อบังคับตลอดทั้งเฟส

- Go 1.25 · Gin · uber/fx · sqlx + squirrel · PostgreSQL 18 · Zap · Viper
- เงินเป็น `decimal.Decimal` ห้าม `float64` ทุกชั้นรวมถึงขอบ JSON
- Clean Architecture: `internal/domain/payout` ห้าม import adapter หรือ service
- ทุกการเปลี่ยนสถานะเป็น guarded `UPDATE` คู่กับ `CheckRowsAffectedWith`
- ห้าม log API key, secret หรือข้อมูลลับของ merchant ทุกระดับรวมถึงตอน error
- **ห้ามเปิด network connection ไปหาธนาคารในเฟสนี้**

## 4. สัญญา (contract)

### 4.1 Request

`POST /api/v1/payout/create` มี header `x-api-key` และ
`Content-Type: application/json` ผ่าน `middleware.SignatureRequired`
เหมือน `POST /deposit/create` เป๊ะ เพราะเงินเคลื่อนที่ตรงนี้

| ฟิลด์ | ชนิด | บังคับ | หมายเหตุ |
|---|---|---|---|
| `clientId` | string | ✅ | ต้องมีจริง **และ**ต้องเป็นของ merchant ที่ล็อกอินอยู่ |
| `merchantId` | string | ✅ | ต้องตรงกับ `Code` ของ merchant ที่ล็อกอิน |
| `transactionId` | string | ✅ | เลขออเดอร์ของ merchant เอง ห้ามซ้ำภายใน merchant เดียวกัน |
| `bankAccountNumber` | string | ✅ | บัญชีปลายทาง |
| `amount` | number | ✅ | อ่านผ่าน `json.Number` ไม่ผ่าน `float64` |
| `bankName` | string | ✅ | ธนาคารปลายทาง สะกดตาม `ListBank.md` |
| `name` | string | ✅ | ชื่อจริงของเจ้าของบัญชีปลายทาง |
| `phone` | string | — | ส่ง `""` ถ้าไม่มี |
| `callbackUrl` | string | ✅ | HTTPS เท่านั้น เก็บไว้ตอนนี้ ใช้จริงใน P4c |
| `signature` | string | ✅ | HS256 ครอบ body ใช้ครั้งเดียว |
| `timestamp` | integer | ✅ | หน่วย ms ต้องตรงกับ `iat` ในลายเซ็น |

### 4.2 Response — 201

รูปแบบตาม PRD เป๊ะ (`status`, `message`, `data` ที่มี `customerData` และ
`systemBankData`)

`referenceId` เป็น base62 สิบตัว จาก `crypto.RandomCode` ตัวเดียวกันและความยาว
เดียวกับที่ `deposits` ใช้

`amount` **ขาเข้าเป็นตัวเลข ขาออกเป็นสตริง** ตั้งใจให้ต่างกัน และเป็นสิ่งที่
`merchantdeposit` ทำอยู่แล้ว: ขาเข้าอ่านผ่าน `json.Number` เพื่อไม่ให้กลายเป็น
`float64` ระหว่างทาง ขาออกเป็นสตริงเพื่อพิมพ์ `decimal.Decimal` ที่เก็บไว้ออกมา
ตรงๆ ไม่มี encoder มาคั่นระหว่างบัญชีกับ merchant

**ทำไม P4a ต้องเลือกบัญชีต้นทางทั้งที่ยังไม่ใช้** — เพราะ PRD บังคับให้ response
บอก `systemBankData` คือบัญชีที่จะจ่าย เพราะฉะนั้นต้องเลือกตั้งแต่ตอนสร้าง บันทึกลง
แถว แล้วส่งกลับ P4b จะใช้บัญชีที่บันทึกไว้ ไม่เลือกใหม่ — ซึ่งแปลว่าคำตอบที่ merchant
เก็บไว้ยังจริงอยู่แม้ config จะเปลี่ยนทีหลัง

### 4.3 Endpoint สำหรับอ่าน

- `GET /api/v1/payout/:reference_id` — ดูรายการเดียว
- `GET /api/v1/payouts` — ดูเป็นหน้า ตาม contract ของ `repository/base`

ทั้งคู่ **ไม่ต้องใช้ signature** เพราะมีแต่ `create` ที่ขยับเงิน — กฎนี้ P3 ตั้งไว้แล้ว

## 5. ตาราง `payouts`

โครงสร้างเต็มอยู่ในฉบับภาษาอังกฤษ ประเด็นที่ต้องเข้าใจ:

- `reserved_fee` — ค่าธรรมเนียมที่ `PostPayoutCreated` กันไว้จริง **ต้องเก็บ** เพราะ
  คอมเมนต์ของ `PayoutInput.ReservedFee` เขียนขอไว้ตรงๆ ว่า *"The full fix is P4
  persisting this on the payout row"* ถ้าอัตราของ merchant ขยับระหว่างที่รายการ
  ค้างอยู่ การคำนวณใหม่ตอนจบจะปิดยอดด้วยตัวเลขคนละตัวกับที่กันไว้ →
  ส่วนต่างค้างใน `pending_payout` ตลอดกาล
- `payouts_merchant_transaction` — `transactionId` ห้ามซ้ำภายใน merchant เดียวกัน
  ไม่ใช่ทั้งระบบ เพราะสอง merchant ตั้งเลขออเดอร์ชนกันได้เป็นเรื่องปกติ
- CHECK ของ `status` รับทุกค่าไว้ตั้งแต่แรก แม้ P4a จะเขียนแค่ `PENDING` เพื่อให้
  P4b/P4c ไม่ต้องมาขยาย CHECK ทีหลัง — เป็นวิธีเดียวกับที่ `deposits_status` ทำ

### 5.1 ทำไม `bank_order_id` กับ `confirmed_at` ต้องมีตั้งแต่ P4a

สองคอลัมน์นี้ **เฟสนี้ไม่เขียนเลย** แต่ต้องประกาศตั้งแต่ตอนสร้างตาราง เพราะมันคือกฎ
ที่ตัดสินว่าเงินคืน merchant ได้หรือยัง:

> `confirmed_at IS NULL` — ยังไม่เคยสั่งธนาคารให้จ่าย คืนเงินได้ปลอดภัย
>
> `confirmed_at IS NOT NULL` — เงินอาจออกไปแล้ว **ต้องมีหลักฐานเชิงบวกเท่านั้น**
> ห้ามคืนเงินเพราะ "ไม่เห็นรายการ"

ถ้าไปเพิ่มทีหลังตอนเขียนโค้ดที่ใช้มัน มันจะกลายเป็นแค่ธรรมเนียมการเขียนโค้ด แต่ถ้า
ประกาศพร้อมตาราง คู่กับ CHECK ที่บังคับว่า confirm แล้วต้องมีเลข order เสมอ
มันจะกลายเป็นคุณสมบัติของข้อมูล

## 6. ขั้นตอนตอนสร้าง

handler ลอกโครง `merchantdeposit.Handler.create` ทีละขั้น เพราะคุณสมบัติด้าน
ความปลอดภัยที่มันสร้างไว้คือสิ่งที่ endpoint นี้ต้องการเหมือนกัน และแต่ละข้อมาจาก
การรีวิวที่เจอของจริง ไม่ใช่ออกแบบมาแต่แรก

1. ตรวจ signature และเก็บ body ตัวที่ลายเซ็นครอบไว้
2. แกะ JSON และ validate DTO
3. ปฏิเสธ `callbackUrl` ที่ไม่ใช่ HTTPS (ไม่สนตัวพิมพ์ใหญ่เล็ก) ก่อนถึง service
4. ปฏิเสธถ้า `merchantId` ระบุคนอื่น — body มาจากผู้เรียก เชื่อไม่ได้
5. ปฏิเสธถ้า `clientId` เป็นของ merchant อื่น — **"มีอยู่จริง" เป็นแค่ครึ่งเดียวของการตรวจ**
6. แปลง `amount` ผ่าน `json.Number`
7. `idem.Begin` จอง `transactionId` ก่อนทำอะไรที่มีผลข้างเคียง ถ้าเป็นการยิงซ้ำ
   คืนคำตอบที่บันทึกไว้ตามเดิม ไม่สร้างใหม่
8. `payout.Service.Create(...)` ← **งานใหม่มีแค่ข้อนี้**
9. `idem.Finish` บันทึกคำตอบ ถ้าล้มเหลวแบบลองใหม่ได้ให้ `Release` คืนสิทธิ์

### 6.1 ข้างใน `Service.Create`

```
validate                                        → 400
หาบัญชีต้นทางจาก config                          → 503 ถ้าไม่มี/ไม่ ACTIVE
เปิด transaction
    ล็อกบัญชี operate ของ merchant นี้            ← กันชนกัน และเป็นยอดที่ใช้
                                                    เช็กด้านล่างด้วย
    insert แถว payout เป็น PENDING
    PostPayoutCreated                            → คืนค่าธรรมเนียมที่กันไว้
    ยอด + ค่าธรรมเนียม > ยอดคงเหลือ               → 422
    เขียน reserved_fee กลับลงแถว
commit
```

ยอดคงเหลือที่ใช้เช็กคือ `operate.Balance` ที่อ่าน **ตอนล็อก** คือยอด **ก่อน**
posting นี้จะตัดเงิน ไม่ใช่ยอดที่คำนวณใหม่หลัง `PostPayoutCreated` รันเสร็จ
(ถ้าใช้ยอดหลัง posting จะกลายเป็นเทียบเงินที่กันไว้กับตัวมันเอง) การเช็กอยู่
หลัง insert และหลัง posting ไม่ใช่ก่อน เพราะค่าธรรมเนียมยังไม่รู้จนกว่า
`PostPayoutCreated` จะรันเสร็จ ลำดับนี้ปลอดภัยได้ก็เพราะทั้งหมด — insert,
posting, และการเช็ก — อยู่ใน transaction เดียวกัน: ถ้าเช็กแล้วเงินไม่พอ
posting และแถวที่ insert ไปจะถูก rollback พร้อมกันหมด ทำให้ payout ที่เงินไม่พอ
ไม่เหลือทั้งแถวและ ledger entry ไว้เลย `TestCreate_Integration_AFailureLeavesNoRowAndNoEntry`
คือตัวที่พิสูจน์ว่า rollback นี้ทำงานจริง อย่าเชื่อลำดับนี้โดยไม่มีเทสนั้น

ค่าธรรมเนียมมาจาก `PostPayoutCreated` ไม่ใช่คำนวณเอง เพราะคอมเมนต์ของ
`ReservedFee` บอกชัดว่าการไปคำนวณซ้ำที่อื่นคือความผิดพลาดที่ฟิลด์นี้มีไว้ป้องกัน
และ `chainFor` ก็ไม่ได้ export ออกมา

### 6.2 guard ยอดเงินไม่พอ

**ปัญหา:** `ledger.Repository.MerchantBalances` ไม่รับ transaction — มันอ่านบน
pool ถ้าเรียกมันแล้วค่อยไปตัดเงินใน transaction แยก payout สองรายการที่วิ่งพร้อมกัน
จะผ่าน guard ทั้งคู่แล้วตัดเงินติดลบ

**ทางแก้ — ไม่ต้องเพิ่ม method ใหม่เลย** `ledger_accounts.balance` เป็นคอลัมน์ที่
**เก็บจริง** ไม่ได้คำนวณสดตอนอ่าน และ P2b มีเครื่องมือให้แล้วทั้งคู่:

```go
EnsureMerchantAccount(ctx, tx, merchantID, KindMerchantOperate)   // มีอยู่แล้ว
LockAccounts(ctx, tx, []uuid.UUID)                                 // SELECT ... FOR UPDATE ORDER BY id
```

guard จึงเป็น: หาบัญชี `MERCHANT_OPERATE` ของ merchant ในทรานแซกชัน → ล็อกมัน →
อ่าน `Balance` จากแถวที่ล็อกไว้ **เป็น row lock จริงบนแถวที่ `Post` update จริง**
ไม่ใช่ advisory lock และเป็น **ล็อกตัวเดียวกับที่ `PostPayoutCreated` จะจับอีกที
ในทรานแซกชันเดียวกัน** จึงไม่ได้สร้างระบบล็อกใหม่ขึ้นมาเลย

payout สองใบของ merchant เดียวกันจึงเข้าคิวกัน: ใบที่สองรอที่ `operate` จนใบแรก
commit แล้วค่อยอ่านยอดที่สะท้อนการกันเงินของใบแรกไปแล้ว

**เรื่องลำดับล็อก** (คอมเมนต์ของ `LockAccounts` เตือนไว้เอง): ทุกการสร้าง payout
จับ `operate` ก่อนเสมอ แล้วปล่อยให้ `Post` จับชุดเต็มเรียงตาม id ทั้งสองฝ่ายจับ
ล็อกแรกตัวเดียวกัน จึงเข้าคิว ไม่ deadlock

`ErrInsufficientBalance` **มีอยู่แล้ว** ใน `internal/domain/ledger/errors.go` ประกาศ
ทิ้งไว้พร้อมคอมเมนต์ที่ระบุชื่อ `PostPayoutCreated` ว่าเป็นคนที่จะต้องใช้ เฟสนี้คือคนนั้น

**เทียบกับ ยอด + ค่าธรรมเนียม ไม่ใช่ยอดอย่างเดียว** ด้วยเหตุผลเดียวกับที่
`PostPayoutCreated` กันทั้งสองอย่าง: merchant ที่จ่ายไหวแค่ยอดแต่ไม่ไหวค่าธรรมเนียม
คือจ่ายไม่ไหว

### 6.3 การเลือกบัญชีต้นทาง

```yaml
payout:
  enabled: false           # ปิดไว้ก่อน เหมือนทุกสวิตช์ที่ขยับเงินตั้งแต่ P3
  source_account_id: ""    # bank_accounts.id ของบัญชีนิติบุคคลที่ใช้จ่ายออก
```

**ใช้ id ไม่ใช่ชื่อ** เพราะ `bankaccount.Service` ไม่มี lookup ด้วยชื่อเลย และ
`bank_accounts.name` ถึงจะ UNIQUE แต่**แก้ได้** ถ้าใครเปลี่ยนชื่อบัญชีในหลังบ้าน
payout จะเงียบๆ ไปชี้บัญชีอื่นหรือพังทั้งหมด id เปลี่ยนด้วยการ rename ไม่ได้ และ
`GetByID` มีอยู่แล้ว จึงไม่ต้องเพิ่ม method ใหม่ให้ port ไหนเลย

ส่วน `SelectOutbound` ที่มีอยู่ใช้ตรงนี้ไม่ได้ เพราะกรอง `tier = 'OUTBOUND'`
ซึ่งตอนนี้ไม่มีสักบัญชี และต้องการยอดคงเหลือที่สดกว่า `pool.balance_refresh_interval`
จาก loop ที่ปิดอยู่

- ว่าง แปลงเป็น UUID ไม่ได้ หรือชี้ไปบัญชีที่ไม่มี → 503 **ไม่สร้างแถว payout**
- บัญชีไม่ `ACTIVE` → 503 เหมือนกัน
- **tier ไม่ใช่ `OUTBOUND` → log warn แล้วไปต่อ**

ข้อสุดท้ายตั้งใจ เพราะตอนนี้ยังไม่มีบัญชี `OUTBOUND` และ dev ใช้บัญชี `INBOUND`
ใบเดียวที่ลงทะเบียนไว้ทำทั้งสองทาง ถ้าปฏิเสธ เฟสนี้จะทดสอบไม่ได้เลย ถ้าปล่อยเงียบๆ
การตั้งค่าผิดบน production จะถูกซ่อน — warn ทุกครั้งที่สร้างจึงดังพอให้เห็น และเบาพอ
ให้เมินได้ตอน dev

`UNIQUE (bank_code, account_no)` บน `bank_accounts` แปลว่าบัญชีจริงใบเดียวมีทั้ง
แถว `INBOUND` และ `OUTBOUND` พร้อมกันไม่ได้ นี่คือเหตุผลที่ไม่ใช้ tier เป็นตัวเลือก

### 6.4 `REJECTED` ในเฟสนี้

`REJECTED` แปลว่า **"เราไม่เคยถามธนาคาร"** เป็นสถานะปลายทางเดียวที่ P4a สร้างได้
ในทางทฤษฎี — แต่เฟสนี้ไม่มีอะไรสร้างมันจริง เพราะทุกการปฏิเสธเกิดก่อน insert แถว
และตอบเป็น HTTP error แทน

ที่นิยามไว้ตรงนี้แทนที่จะไปนิยามใน P4b เพราะเส้นแบ่งที่มันขีดเป็นส่วนหนึ่งของสัญญา
กับ merchant: `rejected` บอกว่า *เราไม่ได้ลอง* · `failed` บอกว่า *เราลองแล้วไม่ผ่าน*
ทั้งคู่คืนเงินที่กันไว้เหมือนกัน แต่เล่าคนละเรื่อง และ PRD ระบุไว้ทั้งสองค่า

## 8. การทดสอบ

Gate คือ `make check` + `make test-integration`

สิ่งที่ต้องพิสูจน์ให้ได้ นอกเหนือจากเคสปกติ:

- **guard ยอดเงินกันชนกันได้จริง** — เรียก `Create` พร้อมกันสองครั้งกับ merchant ที่
  มีเงินพอแค่รายการเดียว ต้องได้ payout หนึ่งใบกับ 422 หนึ่งครั้ง
  **ต้องพิสูจน์กับฐานข้อมูลจริงด้วยสอง transaction — mock สอบตกข้อนี้ไม่ได้**
- **กันเงิน = ยอด + ค่าธรรมเนียม** — fixture ที่ค่าธรรมเนียมเป็นศูนย์พิสูจน์อะไรไม่ได้
  merchant ที่ใช้ทดสอบต้องมีอัตราไม่เป็นศูนย์ และตัวเลขที่กันต้องต่างจากยอด
- **`reserved_fee` คือค่าที่ `PostPayoutCreated` คืนมา** ไม่ใช่ค่าที่คำนวณใหม่ —
  เปลี่ยนอัตราของ merchant ระหว่างกลาง แล้วตัวเลขที่เก็บต้องไม่ขยับ
- **rollback แล้วต้องไม่เหลืออะไร** ไม่มีแถว payout ไม่มี journal entry
- **`journal_entries_reference_unique` ปฏิเสธ `PAYOUT_CREATED` ใบที่สอง** ใต้
  reference เดียวกัน
- **ยิง `transactionId` ซ้ำต้องได้คำตอบที่บันทึกไว้** ไม่ใช่ reference ใหม่

Mutation testing ใช้เหมือนที่ทำมาตลอด P3: reviewer **ออกแบบ mutation ของตัวเอง**
ไม่ใช่ไล่ตามลิสต์ รันด้วย `go test -overlay` กับไฟล์ที่ copy มาแก้ และถือว่า mutation
ที่รอดคือ finding เกี่ยวกับเทสต์ **fixture ที่ทำให้สองค่าบังเอิญเท่ากัน** (ยอดเท่ากับ
ค่าธรรมเนียม, ธนาคารปลายทางเท่ากับธนาคารต้นทาง) จะปลดอาวุธ mutation แบบสลับค่า
ทั้งหมดเงียบๆ ต้องสร้างให้ต่างกันตั้งแต่แรก

## 9. สิ่งที่เฟสนี้จงใจปล่อยให้ค้าง

payout ที่สร้างจาก P4a จะค้างที่ `PENDING` ตลอดไป และเงินจะถูกกันไว้ตลอดไป
ไม่มี worker ไม่มีหมดอายุ ไม่มีทางปล่อยคืนนอกจากแอดมินลง adjustment ใน ledger

**นี่คือสถานะปลายทางที่ถูกต้องของเฟสนี้ และปลอดภัย** เพราะเงินเป็นของ merchant เอง
ถูกกันไว้อย่างเห็นได้ใน `pending_payout` ไม่ได้หายไปไหน และ `POST /payout/create`
ส่งไปพร้อม `payout.enabled: false` เพราะฉะนั้นไม่มี merchant คนไหนไปถึงมันได้ก่อน
P4b จะมีตัวตน
