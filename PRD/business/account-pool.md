# Account Pool Management & Architecture

## 1. คำนวณและประเมินภาพรวมธุรกรรม (Scale Assessment)

เมื่อรวมทั้ง 15 Tenants ตัวเลขธุรกรรมจะอยู่ในระดับ Enterprise Scale:

- **ยอดรับเข้า (Deposit):** ประมาณ 7.5 – 22.5 ล้านบาท / วัน (หรือ ~225 – 375 ล้านบาท / เดือน)
- **ยอดจ่ายออก (Payout):** ประมาณ 7.5 – 15 ล้านบาท / วัน (หรือ ~225 – 300 ล้านบาท / เดือน)

### ข้อจำกัดที่ต้องระวัง (Bottlenecks):

- **ความถี่รายการ (Transaction Frequency):** หากรวมเงินเข้าบัญชีเดียว วันละหลายพันถึงหมื่นรายการ จะเสี่ยงต่อการถูก Flag ตรวจสอบจากฝ่าย Compliance ของธนาคาร
- **เศษสตางค์ชนกัน (Collision ใน Dynamic QR):** หากมีลูกค้าฝากยอดเท่ากัน (เช่น 500 บาท) เข้ามาพร้อมกันหลายสิบคนในบัญชีเดียวกัน เศษสตางค์ ($\pm 1.99$) จะไม่พอสุ่ม ทำให้รายการซ้ำและ Match ยอดพลาด
- **ความเสี่ยงล้มทั้งกระดาน (Domino Effect):** หากใช้บัญชีรวมเพียง 1–2 บัญชี แล้วเกิดปัญหาถูกระงับ ธุรกิจของทั้ง 15 Tenants จะหยุดชะงักทั้งหมด

## 2. โครงสร้างการแบ่งแยกเลเยอร์บัญชี (3-Tier Account Architecture)

> **ข้อกำหนดสำคัญ:** ห้ามใช้บัญชีเดียวทำทั้งรับและจ่ายพร้อมกัน ควรแบ่งโครงสร้างบัญชีออกเป็น 3 เลเยอร์:

```text
┌──────────────────────────────────────────────────────────────────────────┐
│             Tier 1: Inbound Pool (บัญชีหน้าบ้าน - รับเงินฝาก)              │
│       [บจก. A (บช.1)]       [บจก. B (บช.2)]       [บจก. C (บช.3)]        │
└────────────────────────────────────┬─────────────────────────────────────┘
                                     │ Auto-Sweep (กวาดเงินเมื่อแตะเกณฑ์)
                                     ▼
┌──────────────────────────────────────────────────────────────────────────┐
│             Tier 2: Vault / Master Pool (บัญชีพัก / คลังเงินกลาง)          │
│                [บจก. หลัก / บัญชีควบคุมสภาพคล่อง (Liquidity)]             │
└────────────────────────────────────┬─────────────────────────────────────┘
                                     │ Auto-Topup (เติมเงินตามรอบ)
                                     ▼
┌──────────────────────────────────────────────────────────────────────────┐
│             Tier 3: Outbound Pool (บัญชีหลังบ้าน - จ่ายเงิน Payout)       │
│       [บจก. D (บช.4)]       [บจก. E (บช.5)]       [บจก. F (บช.6)]        │
└──────────────────────────────────────────────────────────────────────────┘
```

### คำอธิบายหน้าที่ของแต่ละ Tier:

- **Inbound Pool (รับฝากเงินอย่างเดียว):** บัญชีสำหรับโชว์หน้าบ้าน (Dynamic QR / Transfer) โดยไม่มีการสั่ง Payout ออกจากบัญชีนี้ ช่วยให้ Statement ฝั่งเงินเข้าสะอาด ไม่มีประวัติโอนออกกระจายตัว
- **Vault / Settlement Account (คลังพักเงินกลาง):** บัญชีพักเงินภายใน ไม่เปิดเผยให้คนนอกรู้ ใช้พักเงินที่กวาดมาจากหน้าบ้าน และคอยจ่ายเติมสภาพคล่องไปให้หลังบ้าน
- **Outbound Pool (จ่ายเงินออก Payout อย่างเดียว):** บัญชีที่มีวงเงินโอนออกสูง เชื่อมต่อ Direct API สั่ง Payout จะไม่มีเงินก้อนใหญ่แช่อยู่ แต่จะรับเติมเงินเข้ามาทีละรอบตามปริมาณที่ต้องจ่ายออกจริง เพื่อจำกัดความเสี่ยง

## 3. กลยุทธ์การหมุนวงบัญชีและการจัดสรร Tenant (Pool Routing Strategy)

### 3.1 การแบ่งกลุ่ม Tenant (Tenant Clustering)

ไม่ควรให้ทั้ง 15 Tenants ยิงเข้า Pool เดียวกันแบบกวนรวม ควรจัดเป็น Cluster (เช่น 1 Cluster = 3–5 Tenants):

- **Cluster 1 (Tenant 1–5):** ใช้ Inbound Pool ชุดที่ 1 + Outbound Pool ชุดที่ 1
- **Cluster 2 (Tenant 6–10):** ใช้ Inbound Pool ชุดที่ 2 + Outbound Pool ชุดที่ 2
- **Cluster 3 (Tenant 11–15):** ใช้ Inbound Pool ชุดที่ 3 + Outbound Pool ชุดที่ 3

> **ข้อดี:** หากบัญชีใน Cluster ใดมีปัญหา อีก 10–12 Tenants จะยังคงรันต่อได้ 100%

### 3.2 กฎการหมุนเวียนบัญชี (Smart Rotation Logic)

- **Volume Threshold Rotation (สลับตามเพดานยอดเงิน):** กำหนดเพดาน เช่น เมื่อบัญชีรับเงินแตะ 3,000,000 บาท/วัน หรือ 1,500 รายการ/วัน ระบบจะปลดบัญชีนั้นเข้าสู่สถานะ Cooling Down (พักบัญชี) และสลับบัญชีสำรองขึ้นมาแสดงผลหน้าเว็บแทน
- **Round-Robin for Dynamic QR (กระจายลดการชนของเศษสตางค์):** เมื่อลูกค้า 2 คนกดฝาก 500 บาทพร้อมกัน:
  - คนที่ 1 ได้รับ QR บัญชี บจก. A (ยอด 500.25)
  - คนที่ 2 ได้รับ QR บัญชี บจก. B (ยอด 500.10)
  - _ช่วยขยายพื้นที่สุ่มเศษสตางค์ได้ไม่จำกัด และไม่มีทางที่เศษสตางค์จะชนกัน_
- **Failover / Health Check Switching:** หาก API แจ้งเตือนว่าบัญชีใดมีข้อผิดพลาด (เช่น บัญชีติดสถานะตรวจสอบ) ระบบ Gateway จะตัดบัญชีนั้นออกจาก Pool อัตโนมัติ และสลับ Payout ไปออกบัญชีอื่นทันทีในระดับวินาที

## 4. การจัดการสภาพคล่อง (Automated Liquidity & Sweeping)

- **Auto-Sweeping (กวาดเงินเข้าคลัง):** เมื่อบัญชี Inbound รับเงินสะสมครบตามเกณฑ์ (เช่น ทุกๆ 500,000 บาท หรือทุก 2 ชั่วโมง) ระบบจะสั่งกวาดเงินอัตโนมัติเข้ามาที่ Vault บัญชีกลาง เพื่อไม่ให้มียอดเงินค้างหน้าบ้านเยอะเกินไป
- **Just-In-Time Top-up (เติมเงินพร้อมจ่าย):** บัญชี Outbound จะคงยอดเงินไว้เพียงพอจ่ายประมาณ 1–2 ชั่วโมง (เช่น บัญชีละ 300,000 – 500,000 บาท) เมื่อยอดเงินในบัญชี Outbound ลดลงต่ำกว่า Minimum Balance (เช่น เหลือต่ำกว่า 50,000 บาท) ระบบจะดึงเงินจาก Vault มาเติมให้ทันที ทำให้การจ่ายเงินไม่สะดุด

## 4. Merchant-to-Corporate Architecture & Account Isolation Strategy (การจัดสรรบัญชี บจก. และ User ต่อ 1 Merchant)

### 4.1 แนวคิดการแยกอิสระ (Account Isolation Principle)

เพื่อตัดปัญหาข้อมูลและยอดเงินปนกันระหว่างพาร์ทเนอร์ (Zero Cross-Tenant Contamination) ระบบแยก Ledger ตาม Merchant แต่ **บัญชี บจก. ไม่ได้ผูกแบบ 1:1 กับ Merchant**[cite: 2]:

```
Merchant (1)  ──►  บัญชี บจก. (N)  ──►  User / Sub-User (N)
```

- **1 Merchant มีได้หลายบัญชี บจก.:** ใช้รับเงิน จ่ายเงิน สำรอง และ Failover ในชุดของ Merchant นั้นโดยไม่ปะปนกับ Merchant อื่น
- **1 บัญชี บจก. มีได้หลาย User:** Master Admin, Maker, Approver, Inquiry ผูกสิทธิ์กับบัญชีนั้น
- **อิสระในการกระทบยอด:** Statement ของแต่ละบัญชี บจก. แยกชัด แต่ Ledger ระดับ Merchant รวมยอดจากทุกบัญชีที่ผูกไว้
- **การจำกัดความเสี่ยง (Risk Containment):** หากบัญชีหนึ่งถูกระงับ Gateway สลับไปบัญชีอื่นในพูลของ Merchant เดียวกันได้ทันที โดยไม่กระทบ Merchant อื่น

---

### 4.2 การเปรียบเทียบ 2 แผนการจัดโครงสร้างบัญชีต่อ 1 บจก. (Architecture Trade-offs)

| มิติการเปรียบเทียบ                 | ทางเลือกที่ 1: Single-Account Model (1 บัญชี รวม In/Out)                  | ทางเลือกที่ 2: Dual-Account Model (2 บัญชี แยก In/Out)          |
| :--------------------------------- | :------------------------------------------------------------------------ | :-------------------------------------------------------------- |
| **โครงสร้างต่อ Merchant**         | 1 Merchant ผูก **หลาย บช. บจก.** ได้; แต่ละ บจก. ใช้ 1 บัญชีรวมรับ-จ่าย | 1 Merchant ผูก **หลาย บช. บจก.** ได้; แต่ละ บจก. แยกรับ + จ่าย |
| **Users ต่อ 1 บช. บจก.**          | **หลาย User** (Master / Maker / Approver / Inquiry)                      | **หลาย User** ต่อทั้งบัญชีรับและบัญชีจ่าย                        |
| **ความซับซ้อนในการตั้งค่า**        | ต่ำ–ปานกลาง (เพิ่มบัญชีในพูลได้ตามโวลุ่ม)                               | สูงกว่า (แยกฟังก์ชันรับ-จ่าย + หลายบัญชีสำรอง)                 |
| **การจัดการสภาพคล่อง (Liquidity)** | **อัตโนมัติ 100%** (เงินฝากเข้ามาถูกนำไปจ่าย Payout ได้ทันที)[cite: 2, 7] | **ต้องคอยย้ายเงิน** (ต้องโอนเงินจากบัญชีรับไปเติมบัญชีจ่าย)     |
| **ความสะอาดของ Statement**         | ข้อมูลเงินเข้าและเงินออกผสมกันในบัญชีเดียว                                | **สะอาดและตรวจสอบง่าย** (แยกรายการ Inbound และ Outbound ชัดเจน) |
| **ความเสี่ยงระบบตรวจจับ**          | ปานกลาง (มีความถี่ทั้งเงินเข้าและเงินออกหมุนเวียนต่อเนื่อง)               | **ต่ำมาก** (บัญชีรับไม่มีพฤติกรรมโอนออกกระจายตัว)[cite: 1, 2]   |
| **จำนวนบัญชีรวม (15 Merchants)**   | **หลายบัญชีต่อ Merchant** (เช่น Merchant ละ 2–4 บัญชี รวม ~30–60)     | **หลายบัญชีต่อ Merchant** (แยกรับ-จ่าย + สำรอง รวมสูงกว่า)     |

### 4.3 รายละเอียดแนวทางการดำเนินงาน (Detailed Plan Architecture)

#### แผน A: Single-Account Hybrid Model (หลาย บช. บจก. / 1 Merchant - แต่ละบัญชีรวมรับและจ่าย)

- **รูปแบบการทำงาน:**
  - Merchant ผูกได้หลายเลขบัญชี แต่ละบัญชีใช้ทั้งสร้าง Dynamic QR / Transfer Deposit และเชื่อม Direct Corporate API สำหรับ Auto-Payout
  - Gateway หมุนเวียน (Round-Robin / Threshold) ระหว่างบัญชีในพูลของ Merchant
- **ข้อดี:** ไม่ต้องมีขั้นตอนการโยกเงินข้ามบัญชีภายใน เงินที่รับเข้าสามารถรองรับคำขอถอนเงินได้ทันทีแบบ Real-time[cite: 2, 7]
- **แนวทางควบคุมความเสี่ยง:** ตั้งระบบแจ้งเตือนเมื่อยอดธุรกรรมรวมต่อวันใกล้แตะเพดานที่ตกลงไว้กับธนาคาร แล้วสลับไปบัญชีอื่นในพูล

#### แผน B: Dual-Account Dedicated Model (หลาย บช. บจก. / 1 Merchant - แยกรับและจ่าย)

- **รูปแบบการทำงาน:**
  1. **Inbound Account (บัญชีรับเงิน):** ใช้สำหรับ Dynamic QR และ Transfer Statement Matching เท่านั้น ไม่เปิดสิทธิ์โอนเงินออก[cite: 1, 2, 7] — มีได้หลายบัญชีต่อ Merchant
  2. **Outbound Account (บัญชีจ่ายเงิน):** ผูกกับ Direct API สำหรับ Auto-Payout เท่านั้น ไม่เปิดเผยเลขบัญชีหน้าบ้าน[cite: 1, 2, 7] — มีได้หลายบัญชีต่อ Merchant
- **ข้อดี:** ป้องกันการระงับบัญชีได้ดีที่สุด Statement โปร่งใส และลดความผิดพลาดด้านระบบบัญชี[cite: 1, 2]
- **กระบวนการจัดการเงิน:** กำหนดรอบโยกเงินภายใน (Internal Sweep) จากบัญชีรับเข้าสู่บัญชีจ่ายตามรอบเวลาหรือระดับยอดเงินคงเหลือ

### 4.4 การจัดสรร Credential และการเชื่อมต่อ (Merchant / Account / User Mapping)

```
[ Merchant Platform ]
│
│ Request (x-api-key, HS256 Signature, Merchant ID)[cite: 2, 7]
▼
┌─────────────────────────────────────────────────────────────┐
│ Payment Gateway Isolation Core                                │
│ - ดึงพูลบัญชี บจก. ของ Merchant จาก Merchant ID               │[cite: 2, 7]
│ - เลือกบัญชีตาม Routing / Failover                             │
│ - ใช้ User ของบัญชีนั้น (Maker / Approver / Inquiry)          │
│ - ตรวจสอบความถูกต้องของ Digital Signature                       │[cite: 2, 7]
└──────────────────────────────┬──────────────────────────────┘
                 │
     ┌───────────┴───────────┐
     ▼                         ▼
  บช. บจก. #1              บช. บจก. #2
  Users: N คน               Users: N คน
```

- **API Credentials 1 ชุดต่อ 1 Merchant:** ประกอบด้วย `x-api-key`, `Secret Key`, `Merchant ID` และ `Client ID`[cite: 2, 7]
- **Bank Configuration หลายชุดต่อ 1 Merchant:** แต่ละบัญชี บจก. มี Biller ID / ข้อมูลบัญชีกรุงไทย และชุด Sub-User ของตนเอง
- **User หลายคนต่อ 1 บช. บจก.:** สิทธิ์ Inquiry / Maker / Approver ไม่แชร์ข้ามบัญชีโดยอัตโนมัติ เว้นแต่ถูกกำหนดเป็น Master ของหลายบัญชี
- **ไม่แชร์ข้าม Merchant:** บัญชี บจก. และ User ของ Merchant หนึ่งห้ามปะปน Ledger กับ Merchant อื่น
