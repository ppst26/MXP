### **นิยามของ Merchant (Merchant Definition)**
ในระบบเกตเวย์การชำระเงินของ **FLASH-PAY** และ **BIT-PAYZ** คำว่า **Merchant (หรือ Tenant)** หมายถึง **ร้านค้า ผู้ให้บริการแพลตฟอร์ม หรือเจ้าของระบบ** (เช่น เว็บไซต์เดิมพัน หรือระบบ Enterprise SaaS) [cite: 281, 544] ที่นำชุด API ของเกตเวย์ไปเชื่อมต่อเพื่อทำระบบรับเงินฝากเข้า (Inbound/Deposit) และสั่งโอนจ่ายเงินออก (Outbound/Payout) แบบอัตโนมัติ 100% [cite: 281, 544] โดยเปลี่ยนผ่านจากบัญชีบุคคลธรรมดาที่เสี่ยงต่อการโดนอายัดและติดเงื่อนไขสแกนใบหน้า มาใช้งานบน **บัญชีธนาคารนิติบุคคล (บจก.)** ผ่านการเชื่อมต่อ Direct API ร่วมกับธนาคารกรุงไทย (KTB) [cite: 211, 224, 246]

---

### **โครงสร้างบัญชีและผู้ใช้ภายใต้ Merchant (Account & User Hierarchy)**

Merchant เป็นหน่วยธุรกิจหลักของเกตเวย์ **ไม่เท่ากับบัญชี บจก. หนึ่งบัญชี** ระบบบังคับใช้ความสัมพันธ์แบบ 1:N สองชั้นดังนี้:

```
Merchant (Tenant)
  │  merchantId + API Credentials (x-api-key, Secret Key, Client ID)
  │
  ├── บช. บจก. #1  (เช่น Inbound / Dual)
  │     ├── User: Master Admin
  │     ├── User: Maker
  │     ├── User: Approver
  │     └── User: Inquiry
  │
  └── บช. บจก. #2  (เช่น Outbound / สำรอง)
        └── Users ... (หลายคนต่อ 1 บัญชี)
```

| ความสัมพันธ์ | Cardinality | ความหมาย |
| :--- | :--- | :--- |
| **Merchant → บัญชี บจก.** | **1 : N** | Merchant หนึ่งรายผูกบัญชีนิติบุคคลได้หลายบัญชี (รับ, จ่าย, สำรอง, Failover) |
| **บัญชี บจก. → User** | **1 : N** | แต่ละบัญชี บจก. มี Sub-User ได้หลายคน (Master Admin, Maker, Approver, Inquiry) |

*   **Ledger ระดับ Merchant:** ยอด `balance` / `operateBalance` ของ Merchant รวมจากทุกบัญชี บจก. ที่ผูกไว้ แล้วยังแยก Ledger ตาม `merchantId` ไม่ปะปนกับ Merchant อื่น
*   **Credential ระดับบัญชี บจก.:** แต่ละบัญชี บจก. มีชุดเชื่อมต่อ KTB Corporate ของตนเอง (Biller / Corporate Login / Sub-User) ไม่แชร์ข้ามบัญชี
*   **สิทธิ์ระดับ User:** User สังกัดบัญชี บจก. ที่ระบุ ไม่ได้ถือสิทธิ์ทุกบัญชีของ Merchant โดยอัตโนมัติ เว้นแต่ถูกกำหนดเป็น Master ของหลายบัญชี

### **1. ข้อมูลสิทธิ์ความปลอดภัยที่ Merchant ต้องถือครอง (Prerequisites & Credentials)**
เพื่อความปลอดภัยระดับสูงสุดในการเชื่อมต่อระบบแบบ System-to-System Merchant แต่ละรายจะได้รับชุดคีย์ยืนยันสิทธิ์เฉพาะจากเกตเวย์ทั้งหมด **4 ตัว** [cite: 282, 334] (ระดับ Merchant ไม่ใช่ระดับบัญชี บจก.):
*   **`Merchant ID`** *(string)*: รหัสอ้างอิงประจำตัวของร้านค้าที่ระบุตัวตนบนระบบเกตเวย์ [cite: 282, 334]
*   **`Client ID`** *(string)*: รหัสระบุตัวตนระบบย่อยหรืออุปกรณ์ Client ที่ใช้ริเริ่มส่ง Request [cite: 282, 334]
*   **`API Key (x-api-key)`** *(string)*: คีย์สาธารณะสำหรับแนบใน HTTP Header ของทุก Request เพื่อตรวจสอบสิทธิ์เข้าใช้งาน [cite: 282, 334]
*   **`Secret Key`** *(string)*: กุญแจลับส่วนตัวสำหรับใช้คำนวณสร้าง **Digital Signature (HMAC-SHA256)** ภายในระบบหลังบ้านของตนเอง **(ห้ามส่งคีย์นี้ผ่านเน็ตเวิร์กเด็ดขาด)** [cite: 282, 283, 334, 335]

ชุดคีย์นี้ผูกกับ Merchant ทั้งก้อน ส่วนบัญชี บจก. และ User ของแต่ละบัญชีเป็นชั้นถัดไป (ดู Account & User Hierarchy ด้านบน)

### **2. สเปกข้อมูลและพารามิเตอร์การดึงยอดเงินคงเหลือ (GET Get Merchant Balance)**
เกตเวย์จัดสรร API เส้นนี้ไว้สำหรับให้ Merchant ตรวจสอบยอดเงินหมุนเวียนคงเหลือแบบ Real-time เพื่อรักษาสภาพคล่องทางการเงิน โดยยอดที่แสดงเป็นผลรวมจากทุกบัญชี บจก. ที่ผูกกับ Merchant นั้น [cite: 397]

#### **A. ข้อมูลจำเพาะทางเทคนิค (API Specifications)** [cite: 397]
*   **HTTP Method:** `GET` [cite: 397]
*   **Request URL Endpoint:** `{{API_ENDPOINT}}/api/v1/merchant/balance?merchantId={{MERCHANT_ID}}` [cite: 397]
*   **Headers:**
    ```http
    x-api-key: {{YOUR_API_KEY}}
    ```
    *(ตรวจสอบสิทธิ์เข้าถึงข้อมูลของ Merchant [cite: 397])*

#### **B. โครงสร้าง Query Parameters** [cite: 398]
*   **`merchantId`** *(string, ✅ **Required**)*: รหัสระบุตัวตน Merchant ID ประจำร้านค้าของคุณ [cite: 398]

#### **C. นิยามรายละเอียดประเภท Balance ภายในระบบ (Balance Breakdown)** [cite: 397]
ยอดเงินคงเหลือทั้งหมดของ Merchant จะคิดจากสมการ:  
\\[\text{balance} = \text{operateBalance} + \text{parkingBalance} + \text{freezeBalance}\\] [cite: 397]
*   **`balance`**: ยอดเงินสะสมรวมทั้งหมดของ Merchant จากทุกบัญชี บจก. ที่ผูกไว้ [cite: 397]
*   **`operateBalance`**: **วงเงินคงเหลือในบัญชีหลัก** ที่พร้อมใช้งานสำหรับการทำธุรกรรม ฝากเข้า-ถอนออก หรือจ่ายเงิน Payout ได้ทันที [cite: 397]
*   **`parkingBalance`**: วงเงินคงเหลือในบัญชีสำรอง (Secondary Account) หรือบัญชีที่ใช้เป็นจุดพักเงินความถี่ต่ำ [cite: 397]
*   **`freezeBalance`**: ยอดเครดิตหรือเงินส่วนที่มีข้อพิพาทและถูกอายัดหรือระงับสิทธิ์ชั่วคราวโดยระบบ [cite: 397]

#### **D. Example Request (cURL)** [cite: 398]
```bash
curl --location -g 'https://api.flash-pay.io/api/v1/merchant/balance?merchantId=VOBM7qzaRH' \
--header 'x-api-key: SEC_API_KEY_DEMO_01'
```

#### **E. Example Response (200 OK)** [cite: 398]
```json
{
  "status": "success",
  "data": {
    "merchantId": "VOBM7qzaRH",
    "name": "demo2",
    "balance": 428.84,
    "operateBalance": 247.45999999999998,
    "parkingBalance": 0,
    "freezeBalance": 181.38,
    "updatedAt": "2024-10-07T11:21:38.596Z"
  }
}
```

### **3. ขั้นตอนการประมวลผลธุรกรรมของ Merchant (Core Integration Workflows)**

#### **ขั้นตอนที่ 1: การลงนามคำขอ (Signature Generation)**
ก่อน Merchant ส่งคำขอสำคัญ เช่น สร้างยอดฝากหรือ Payout จะต้องลงนามข้อมูลบนระบบของตนเองด้วยรหัส **HS256 (HMAC-SHA256)** โดยใช้ข้อมูล `merchantId`, `clientId`, และเวลาปัจจุบันในหน่วย **Unix Milliseconds (ms)** นำมาเข้ารหัสร่วมกับ `Secret Key` ได้ผลลัพธ์เป็น JWT Signature สำหรับแนบส่งยืนยันตัวตนแบบใช้ครั้งเดียวทิ้ง (Single-use Token) [cite: 283, 311, 335, 369]

#### **ขั้นตอนที่ 2: โฟลว์การรับชำระเงิน (Inbound / Deposit Flow)** [cite: 545]
1.  ลูกค้ากดเลือกฝากเงินหน้าเว็บ Merchant ส่งคำสั่ง `POST /api/v1/deposit/create` ไปยังเกตเวย์ [cite: 291]
2.  กรณีฝากผ่าน **QR** ระบบเกตเวย์จะ **สุ่มเศษสตางค์ในช่วง \\(\pm 1.99\\) บาท** เพื่อเป็นเอกลักษณ์ป้องกันเศษสตางค์ชนกัน (เช่น ฝาก 100 บาท ระบบจะกำหนดให้จ่ายจริง 101.54 บาท) และส่งรหัสสตริงดิบกลับคืนมา [cite: 292, 545]
3.  Merchant Backend นำรหัส QR String นั้นไปแปลงวาดเป็นภาพ QR Code แสดงผลให้ลูกค้าสแกนจ่าย [cite: 291, 545]
4.  กรณีฝากผ่าน **TRANSFER (โอนตรงบัญชี)** เกตเวย์จะใช้เลขบัญชีและชื่อผู้โอนในการตรวจสอบความถูกต้องผ่านสเตตเมนต์จริงอัตโนมัติ [cite: 288, 545]
5.  เมื่อเงินเข้าบัญชี บจก. สำเร็จ เกตเวย์จะส่งสัญญาณอะซิงโครนัส **Webhook Callback** กลับไปปรับยอดเครดิตในเกมให้ลูกค้าของ Merchant ทันที [cite: 289, 545]

#### **ขั้นตอนที่ 3: โฟลว์การจ่ายโอนเงินออก (Outbound / Auto-Payout Flow)** [cite: 546]
1.  เมื่อลูกค้ากดทำรายการถอนเงิน Merchant Backend จะเรียกใช้ Utility ตรวจสอบชื่อบัญชีปลายทาง (`POST /api/v1/client/bank/verify/bankAccountName`) เพื่อความเที่ยงตรง [cite: 287, 546]
2.  หลังบ้าน Merchant ส่งข้อมูลระบุบัญชีผู้รับและยอดเงิน ยิงคำขอ `POST /api/v1/payout/create` พร้อมแนบลายเซ็น Signature [cite: 306, 353, 429]
3.  เกตเวย์รับคำสั่งประมวลผล เลือกบัญชี บจก. จากพูลของ Merchant (Routing / Failover) แล้วสั่งจ่ายทันทีโดยผ่านขั้นตอนสแกนใบหน้าและ No Multi-tier Approval [cite: 544, 546]
4.  เครือข่ายธนาคารโอนเงินสำเร็จ เกตเวย์ส่งสัญญาณ Webhook ยืนยันผลสเตตัสสุดท้ายกลับมาให้พาร์ทเนอร์อัปเดต Ledger บัญชีแบบ Real-time [cite: 304, 546]

#### **ขั้นตอนที่ 4: การแกะรหัสยืนยัน Webhook (Webhook Decryption Verification)**
เมื่อได้รับ Webhook Callback ใดๆ ระบบ Merchant จำเป็นต้องใช้กลไกความปลอดภัยเพื่อตรวจสอบสิทธิ์ ดังนี้ [cite: 395, 549]:
1.  **ดึงค่า `hash` จาก Webhook Payload** [cite: 302, 395] มาทำการถอดรหัสลับด้วยมาตรฐาน **AES-256** โดยมี Key คือการต่อกันของ **`API_KEY` + `SECRET_KEY`** ของร้านค้า [cite: 301, 395, 424]
2.  หากถอดรหัสเรียบร้อยแล้ว ค่า Transaction ID ที่ได้อยู่ข้างใน**ต้องสะกดตรงกันกับค่า `transactionId` ที่ส่งมาเปล่าๆ นอกรหัสอย่างแม่นยำ** จึงจะผ่านสิทธิ์ (ป้องกัน Fake Webhook ยัดสิทธิ์เติมลม) [cite: 395, 549]
3.  **ทำ Idempotency Check:** ดึง `transactionId` ไปค้นสถานะออเดอร์ในตาราง Database ระบบคุณก่อน [cite: 302, 549] หากรายการนั้นถูกระบุว่าสำเร็จเป็น `completed` ไปเรียบร้อยแล้ว **ให้หยุดประมวลผลทันทีและตอบตอบกลับ HTTP 200 OK (แบบ No Body)** เพื่อป้องกันการบวกแต้มหรือตัดยอดเงินเบิ้ลกรณีเกตเวย์ส่งสัญญาณซ้ำครับ [cite: 303, 549]

### **4. สถาปัตยกรรม reseller / ตัวแทนภายนอก (Reseller & Downline Hierarchy)**
ในกรณีที่ Merchant มีการนำ Gateway ไปเชื่อมระบบต่อให้กับสายเครือข่ายภายนอก (External Merchants) ระบบรองรับโมเดลการกระจาย % ดังนี้ครับ [cite: 551, 562]:

```
                     ┌────────────────────────────────────┐
                     │     Master Platform Admin (Root)   │ (ต้นทุน เช่น 0.80%)
                     └─────────────────┬──────────────────┘
                                       │ กำหนดเรตและปล่อย % ต่อ
                                       ▼
                     ┌────────────────────────────────────┐
                     │          Tier 1: Reseller          │ (ได้รับเรตพิเศษ เช่น 1.00%)
                     │   - บริหาร Sub-Merchant ใต้สาย     │
                     │   - ได้รับ Rebate % จากธุรกรรมลูก    │
                     └─────────────────┬──────────────────┘
                                       │ ปล่อยMarkup ต่อ (เช่น 1.80%)
                                       ▼
                     ┌────────────────────────────────────┐
                     │      Tier 2: Direct Merchant       │ (ใช้งาน API ฝาก-ถอน ตรง) [cite: 562]
                     │   - ใช้งานอย่างเดียว (CONSUMER)    │
                     │   - ล็อกสิทธิ์ ห้ามแบ่งสายงานต่อ     │ [cite: 562]
                     └────────────────────────────────────┘
```

1.  **สิทธิ์ Reseller:** สามารถตั้ง Markup อัตราค่าบริการตามชอบให้แก่ Direct Merchant ใน downline ของตนเองได้ (เช่น ต้นทุนระบบอยู่ที่ 0.80% Reseller ไปปล่อยต่อ 1.80%) ซึ่งส่วนต่างกำไร 1.00% จะไหลคืนเป็นยอดเครดิต Rebate ให้ Reseller แบบ Real-time ทุกธุรกรรมของลูกสาย [cite: 562]
2.  **สิทธิ์ Direct Merchant (Downline):** ถือเป็นผู้ใช้งานระบบปลายทาง (Leaf Node) ถูกกำหนดให้อยู่ภายใต้เกณฑ์ **`CONSUMER_ONLY`** มีหน้าที่รับและเรียกใช้สิทธิ์ API ของเกตเวย์ (Deposit/Payout) เท่านั้น [cite: 562] และจะ**ถูกล็อกระบบไม่ให้สร้าง Sub-Agent หรือกระจาย % ต่อยอดเป็นทอดๆ ได้อีกต่อไป** เพื่อความโปร่งใสและตัดปัญหาทับซ้อนของ Ledger บัญชีของระบบ [cite: 562]
