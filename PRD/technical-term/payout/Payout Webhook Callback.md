### **POST Payout Webhook Callback**

---

### **1. นิยามการทำงาน (Definition)**
**POST Payout Webhook Callback** คือ ระบบการส่งสัญญาณแจ้งเตือนผลและอัปเดตสถานะของธุรกรรมเงินโอนออก (Outbound Payout / Withdrawal) แบบอะซิงโครนัส (Asynchronous HTTP POST) จากตัวระบบ Gateway (ทั้ง **FLASH-PAY** และ **BIT-PAYZ**) ส่งตรงไปยังเซิร์ฟเวอร์หลังบ้านของแพลตฟอร์มหรือร้านค้า (ตาม URL ที่ระบุไว้ในฟิลด์ `callbackUrl` ตอนที่ส่งคำสั่งสร้าง Payout ตั้งแต่แรก) [cite: 16, 17, 27] 

โดยระบบจะทำการทริกเกอร์ (Trigger) ส่งข้อมูล Webhook แจ้งเตือนสถานะทันทีเมื่อธุรกรรมเดินทางเข้าสู่สถานะดังต่อไปนี้ [cite: 27]:
*   **`processing`**: อยู่ระหว่างการส่งเรื่องให้เครือข่ายธนาคารดำเนินการหักบัญชีเพื่อตัดยอดโอนเงิน [cite: 17, 27]
*   **`completed`**: เครือข่ายธนาคารดำเนินการโอนยอดเงินเข้าสู่บัญชีธนาคารของลูกค้าปลายทางสำเร็จเสร็จสิ้น [cite: 17, 27]
*   **`failed`**: เกิดข้อผิดพลาดทางการเงินหรือเครือข่ายขัดข้องทำให้ไม่สามารถทำรายการได้สำเร็จ [cite: 17, 27]
*   **`rejected`**: คำสั่งถอนเงินถูกปฏิเสธโดยระบบชำระเงินหลักหรือทางธนาคาร (เช่น บัญชีปลายทางปิดตัว หรือระบบธนาคารปิดปรับปรุง) [cite: 17, 27]

### **2. ขั้นตอนการประมวลผลและการรับส่งข้อมูล (Workflows & Lifecycle)**

```
 [ Merchant Platform (หลังบ้านของคุณ) ]                 [ Payment Gateway Core ]                  [ Core Banking ]
                │                                                │                                       │
  1. ยิงคำสั่งสร้าง Payout                                         │                                       │
  ├─────────────── POST /api/v1/payout/create ──────────────────►│                                       │
  │                (amount, bankInfo, callbackUrl)               │ 2. ตรวจสอบ Signature                  │
  │◄────────────── 200 OK (Status: pending) ─────────────────────┤    และส่งคำสั่งโอนทันที                 │
  │                                                              ├──────── Direct Bank Transfer ────────►│
  │                                                              │         (Status: processing)          │
  │                                                              │                                       │
  │                                                              │ 3. ธนาคารประมวลผลสำเร็จ                │
  │                                                              │◄──────────────────────────────────────┤
  │ 4. รับ Webhook แจ้งผลสถานะสุดท้าย                               │                                       │
  │◄────────────── POST callbackUrl ─────────────────────────────┤ (เปลี่ยนเป็น completed / failed)      │
  │    (พร้อม hash และ qrcode ยืนยันสลิป)                           │                                       │
  ├─────────────── HTTP 200 OK (No Body) ───────────────────────►│                                       │
```

1.  **ขั้นตอนสร้างคำขอ (Initiate Payout):** คุณส่งคำสั่งจ่ายเงินออกผ่าน API `POST /api/v1/payout/create` พร้อมกำหนด `callbackUrl` ไปยัง Gateway [cite: 18]
2.  **ขั้นตอนเข้าคิวธนาคาร:** รายการรับเรื่องจะได้รับการตั้งสถานะเริ่มต้นเป็น `pending` และส่งต่อไปตัดเงินโอนออกจากบัญชีนิติบุคคล (บจก.) ของระบบ [cite: 17, 18]
3.  **ขั้นตอนแจ้งเตือนสเตตัสระหว่งทาง:** ทันทีที่ธนาคารเข้าสู่ขั้นตอนตัดเงิน สถานะจะขยับเป็น `processing` โดยระบบจะส่ง Webhook รอบแรกแจ้งสเตตัสนี้ไปยังเซิร์ฟเวอร์ของคุณ [cite: 17, 27]
4.  **ขั้นตอนแจ้งเตือนสเตตัสสุดท้าย:** เมื่อโอนเงินเข้าบัญชีลูกค้าปลายทางสำเร็จ หรือโอนล้มเหลว ระบบจะยิง Webhook แจ้งสถานะสุดท้ายเป็น `completed` หรือ `failed`/`rejected` ทันที พร้อมกับค่า **`qrcode` ยืนยันสลิปโอนเงิน** (ส่งมาเฉพาะสถานะสำเร็จ) และคีย์ความปลอดภัย **`hash` เพื่อกันการแฮก** [cite: 27, 28]
5.  **ขั้นตอนการตอบกลับจราจร:** เมื่อเซิร์ฟเวอร์หลังบ้านของคุณรับข้อมูลและถอดรหัสตรวจสอบความปลอดภัยถูกต้องแล้ว จะต้องส่งตอบกลับฝั่งเกตเวย์ด้วยรหัสสถานะ **`HTTP 200 OK` แบบ No Body** ทันที เพื่อแจ้งให้ Gateway รับทราบและหยุดการส่ง Webhook ซ้ำรอบถัดไป (Webhook Retry Policy) [cite: 29]

### **3. ข้อมูลจำเพาะทางเทคนิคการรับส่งข้อมูล (Specifications & Payload)**

*   **HTTP Method:** `POST` [cite: 27]
*   **Request URL Endpoint:** `{{client_payout_webhook_url}}` (URL ปลายทางบน HTTPS เซิร์ฟเวอร์ของคุณ) [cite: 27]
*   **Request Headers:**
    *   `Content-Type: application/json`

#### **A. โครงสร้าง JSON Body raw (Request Payload):** [cite: 28]
```json
{
    "referenceId": "qS4EDxSWCO",
    "transactionId": "POP0PTB01776723e7X1",
    "status": "completed",
    "message": "โอนเรียบร้อย",
    "qrcode": "0046000600000101030140225202312086ZwVuYndMYCSnMTv65102TH9104B07F",
    "hash": "U2FsdGVkX19ikrgBKH81gFVP18riN1rjEGACfcuGVra2+AbgePiEj11ZHZ5RBVzi"
}
```

#### **B. คำอธิบายความหมายของตัวแปรข้อมูลทุกฟิลด์ (JSON Field Breakdown):** [cite: 28]
*   **`referenceId`** *(string)*: เลขอ้างอิงธุรกรรมฝั่งผู้ให้บริการระบบหลักเกตเวย์ (แนะนำให้จัดเก็บไว้ใน Ledger คู่กับทรานแซกชันเพื่อทำ Reconcile) [cite: 28]
*   **`transactionId`** *(string)*: รหัสอ้างอิงออเดอร์ของระบบหลักฝั่งคุณที่เจนและส่งอ้างอิงไปตั้งแต่ขั้นตอนแรก (ใช้ดึงสแกนจับคู่อัปเดตสเตตัสในฐานข้อมูล) [cite: 28]
*   **`status`** *(string)*: สถานะล่าสุดของธุรกรรม ณ ขณะรายงานผล (`pending`, `processing`, `failed`, `rejected`, `completed`) [cite: 28]
*   **`message`** *(string)*: บันทึกรายงานเหตุผลขากลับดึงตรงจากธนาคาร เช่น `"โอนเรียบร้อย"` หรือข้อความบ่งชี้เหตุขัดข้อง [cite: 28]
*   **`qrcode`** *(string)*: **รหัสสตรีมใบสลิปการโอนเงิน (Mini-slip QR) ที่รับรองความถูกต้องตรงจากธนาคาร** (ข้อมูลฟิลด์นี้จะมีค่าส่งกลับมา*เฉพาะ*เมื่อสถานะเป็น **`completed`** เท่านั้น) ซึ่งเซิร์ฟเวอร์สามารถแปลงรหัสนี้เป็นรูปภาพ QR Code เพื่อเรนเดอร์แสดงผลบนหน้าจอให้ลูกค้าปลายทางตรวจสอบหรือเซฟเก็บเป็นหลักฐานเงินเข้าได้เลยครับ [cite: 28]
*   **`hash`** *(string)*: ตัวตรวจสอบสิทธิ์ความปลอดภัยสูงสุดเพื่อป้องกัน Webhook ปลอม (Anti-Spoofing) โดยเป็นผลลัพธ์จาก **การนำรหัส `transactionId` ไปเข้ารหัสลับด้วยมาตรฐาน AES โดยใช้คีย์ที่ผสมจากการเชื่อมสัญญากันของข้อความ `API_KEY` + `SECRET_KEY` ของร้านค้าคุณ** [cite: 28]

### **4. ตัวอย่างการรับส่งข้อมูลจริง (Example Request / Response)**

#### **Example Request (cURL):** [cite: 29]
```bash
curl --location -g 'https://your-domain.com/api/v1/payout/callback' \
--header 'Content-Type: application/json' \
--data '{
    "referenceId": "qS4EDxSWCO",
    "transactionId": "POP0PTB01776723e7X1",
    "status": "completed",
    "message": "โอนเรียบร้อย",
    "qrcode": "0046000600000101030140225202312086ZwVuYndMYCSnMTv65102TH9104B07F",
    "hash": "U2FsdGVkX19ikrgBKH81gFVP18riN1rjEGACfcuGVra2+AbgePiEj11ZHZ5RBVzi"
}'
```

#### **Example Response (ฝั่งเซิร์ฟเวอร์หลังบ้านของคุณต้องส่งตอบกลับเกตเวย์):** [cite: 29]
*   **HTTP Status Code:** `200 OK` เท่านั้น [cite: 29]
*   **Response Body:** **ต้องว่างเปล่า (No Response Body)** ห้ามพ่นสายสตริงหรือข้อมูล JSON ใดๆ ขากลับเด็ดขาด [cite: 29]
*   **Response Headers:** **ห้ามระบุ Headers เพิ่มเติม (No Response Headers)** เพื่อจบทราฟฟิกอย่างเสถียรที่สุดครับ [cite: 29]

### **5. สถาปัตยกรรมรักษาความปลอดภัยระดับองค์กร (SaaS Enterprise Security Rules)**

ในการรับสัญญาณ Webhook ธุรกรรมถอนเงินจริง เพื่อหลีกเลี่ยงข้อผิดพลาดและกลลวงทางการเงิน หลังบ้าน Go (Golang) หรือแพลตฟอร์มของคุณต้องวางระบบควบคุม (Control Mechanisms) ดังนี้ครับ:

1.  **ระบบถอดรหัสแกะพิสูจน์สิทธิ์ (Anti-Spoofing AES-256 Decryption):**
    *   **หลักการ:** ทุกครั้งที่ได้รับข้อมูล Webhook ให้ดึงค่า `hash` ไปทำการถอดรหัสย้อนหลังผ่านมาตรฐาน AES-256 [cite: 28] โดยการดึงเอาคีย์ `API_KEY` + `SECRET_KEY` ใน Config ขึ้นมาเป็นกุญแจถอดรหัส [cite: 28] 
    *   **การสอบทาน:** หากถอดรหัสออกมาแล้ว ค่าสตริงข้อมูลที่ได้**ต้องตรงกับตัวแปร `transactionId` ที่แนบมานอกรหัสอย่างเที่ยงตรง** หากถอดรหัสไม่ได้ หรือได้ค่าไม่ตรงกัน ให้ระบบปฏิเสธคำขอทันทีและตั้งสิทธิ์เป็นสลักเป็นผู้บุกรุกเพื่อความปลอดภัยสูงสุด [cite: 28]
2.  **ระบบป้องกันธุรกรรมเบิ้ลสะสม (Idempotency Audit):**
    *   **หลักการ:** การดีเลย์ของเครือข่ายอินเทอร์เน็ตอาจทำให้เกตเวย์คิดว่าส่ง Webhook ไม่ถึงและจะส่งสัญญาณย้ำซ้ำรอบสอง (Retry Transmission) 
    *   **วิธีการแก้:** เมื่อหลังบ้านของคุณได้รับ Payload Webhook ให้ดึง `transactionId` ไปยิงสืบค้นหาประวัติสถานะเดิมใน Database ก่อนเป็นด่านแรก [cite: 211] หากตรวจพบว่าสถานะออเดอร์ดังกล่าวอัปเดตเครดิตเป็น **`completed`** ไปแล้วก่อนหน้า ให้ระบบทำการข้าม (Skip) การปรับยอดเงินกระเป๋าจำลองทันที และส่งตอบกลับ **HTTP Status `200 OK` (แบบว่างเปล่า/No Body)** เพื่อป้องกันความเสี่ยงแต้มลูกค้าหน้าร้านบวมเบิ้ลนั่นเองครับ [cite: 29, 211]
