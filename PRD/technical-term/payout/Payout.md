ในสถาปัตยกรรมระบบ **Enterprise Payment Gateway (SaaS-Ready)** ระบบ **Payout** หรือ **Outbound/Withdrawal Flow (ระบบโอนเงินออก/ระบบสั่งจ่าย)** คือฟังก์ชันระดับวิกฤตที่ออกแบบมาเพื่อจัดการธุรกรรมการเงินขาส่งออกโดยอัตโนมัติ [cite: 11, 21, 154] เพื่อเพิ่มความสะดวก ปลอดภัย และปลดล็อกขีดจำกัดเดิมของการใช้บัญชีบุคคลธรรมดา [cite: 169] โดยมีรายละเอียดการวิเคราะห์เชิงลึกดังนี้ครับ:

---

### 1. Payout คืออะไร? (Definition)

**Payout** คือ กระบวนการส่งคำสั่งโอนเงินจากบัญชีธนาคารนิติบุคคล (บัญชี บจก.) ของแพลตฟอร์มผู้ให้บริการ (เช่น บัญชีธนาคารกรุงไทย KTB Corporate Online) [cite: 11, 126] ไปยังบัญชีธนาคารปลายทางของคู่ค้า สมาชิก ลูกค้า หรือผู้ใช้งานระบบทันทีผ่านการสั่งการทางโปรแกรม (Direct API) [cite: 11, 153, 178] 

กลไกนี้ถูกนำมาใช้ทดแทนระบบบัญชีบุคคลธรรมดา เพื่อปลดล็อกอุปสรรคสำคัญทางธุรกิจ [cite: 169]:
*   **ปลดล็อกเงื่อนไขสแกนใบหน้า (No Face Scan):** หากใช้บัญชีบุคคล การโอนเงินเกิน 50,000 บาท/ครั้ง หรือยอดสะสมเกิน 200,000 บาท/วัน จะบังคับให้สแกนใบหน้าเจ้าของบัญชีจริง ซึ่งขัดขวางระบบอัตโนมัติ [cite: 169] แต่ในสิทธิบัญชี บจก. ของธนาคารจะไม่มีเงื่อนไขนี้ [cite: 169].
*   **รองรับยอดโอนและปริมาณธุรกรรมมหาศาล:** ขยายเพดานยอดโอนออกรายรายการได้สูงถึง 500,000 – 2,000,000+ บาท/ครั้ง [cite: 169] และรองรับความถี่ธุรกรรมรวมได้สูงสุดหลักพันถึงหลายหมื่นรายการต่อวันโดยไม่เสี่ยงโดนบล็อกบัญชี [cite: 169].

### 2. Payout ทำหน้าที่อะไรบ้าง? (Core Capabilities)

ภายใต้ขีดความสามารถของระบบ Gateway (อาทิ มาตรฐาน FLASH-PAY และ BIT-PAYZ) [cite: 11, 21] โมดูล Payout ทำหน้าที่สำคัญดังนี้:

1.  **Direct Auto-Payout (การโอนเงินออกอัตโนมัติทันที):** รับคำสั่งการถอนเงินจากหน้าบ้านของพาร์ทเนอร์/Tenant ยิงประมวลผลคำสั่งส่งให้ธนาคารสั่งโอนออกปลายทางสำเร็จเฉลี่ยในเวลา \\(\le 15\\) วินาทีโดยไม่ต้องรอคนมากดทำรายการ [cite: 170, 175, 178].
2.  **Bank Account Verification (การตรวจสอบบัญชีผู้รับ):** ทำงานร่วมกับ API ยืนยันตัวตน เพื่อสืบค้นชื่อและนามสกุลจริงของผู้ถือบัญชีปลายทางล่วงหน้าด้วยเลขบัญชีและรหัสธนาคาร [cite: 23, 152, 159] ช่วยให้เรามั่นใจว่าเงินโอนจะไม่ตกหล่นหรือโอนผิดบัญชี (Human Error) [cite: 168].
3.  **Virtual Ledger & Reseller Allocation (บริหารเงินแยกสิทธิ์และตัวแทน):** ทำหน้าที่ตัดแบ่งยอดเงินคงเหลือเสมือน (Virtual Wallet Balance) ของแต่ละ Tenant ออกจากกันอย่างอิสระแม้อยู่ในบัญชีรวม [cite: 198] รวมถึงทำหน้าที่คำนวณและตัดแบ่งส่วนต่างค่าธรรมเนียม (Commission Spread Margin) ให้แก่สายตัวแทน Reseller แบบเรียลไทม์ [cite: 202, 206].
4.  **Liquidity & Pre-funding Guard (ควบคุมสภาพคล่อง):** ตรวจสอบยอดเงินสดจริงในบัญชีต้นทางไม่ให้ขาดสภาพคล่อง [cite: 148] โดยดักตรวจสอบเกณฑ์ Buffer Balance เพื่อสกัดรายการไม่ให้ติดสถานะล้มเหลว (failed) [cite: 148, 149].

### 3. Payout ทำงานอย่างไร? (End-to-End Workflow)

กระบวนการทำงานของระบบ Payout ตั้งแต่ต้นทางจนกระทั่งเงินเข้าบัญชีลูกค้าปลายทางและบันทึกปิดรายการ มีขั้นตอนดังนี้ [cite: 23, 154, 178]:

```
[ Merchant Backend (เว็บเดิมพัน) ]                 [ Payment Gateway ]                  [ KTB Corporate ]
              │                                            │                                  │
  1. สร้าง JWT Signature (HS256)                           │                                  │
  2. ยิงคำสั่งถอนเงินทันที                                   │                                  │
  ├─────────────── POST /api/v1/payout/create ─────────────►│                                  │ [cite: 178, 179]
  │                (amount, bankInfo, callbackUrl)          │ 3. ตรวจสอบ Signature             │ [cite: 178, 179]
  │◄────────────── 200 OK (Status: pending) ────────────────┤    และส่งคำสั่งโอนทันที          │ [cite: 178, 179]
  │                                                         ├────── Direct Bank Transfer ─────►│ [cite: 178, 179]
  │                                                         │       (Status: processing)       │ [cite: 178, 179]
  │                                                         │                                  │
  │                                                         │ 4. ธนาคารโอนเงินสำเร็จ           │
  │                                                         │◄─────────────────────────────────┤ [cite: 178, 179]
  │ 5. รับ Webhook แจ้งผล (Status: completed/failed)        │                                  │
  │◄────────────── POST callbackUrl ────────────────────────┤                                  │ [cite: 178, 179]
  │    (พร้อม hash AES-Encrypted & Slip Reference)          │                                  │ [cite: 178, 179]
  ├─────────────── HTTP 200 OK ────────────────────────────►│                                  │ [cite: 178, 179]
```

#### **ขั้นตอนที่ 1: การสร้างคำขอโอนเงินและตรวจสอบสิทธิ์ความปลอดภัย (Request & Security Verification)**
*   เมื่อลูกค้ากดสั่งถอนเงินจากหน้าเว็บ [cite: 175] เซิร์ฟเวอร์หลังบ้านของเราจะจัดเตรียมข้อมูลพารามิเตอร์ที่จำเป็น เช่น `bankAccountNumber` (เลขบัญชีรับเงิน), `bankName` (ชื่อย่อธนาคาร), `amount` (ยอดเงิน), `callbackUrl` (HTTPS สำหรับรับรายงานผล) [cite: 23]
*   **ระบบตรวจสอบความปลอดภัย (Signature Creation):** นำพารามิเตอร์ `merchantId`, `clientId` และ `timestamp` (หน่วยมิลลิวินาที) มาเซ็นลงลายเซ็นความปลอดภัยด้วยกุญแจลับ `Secret Key` ผ่าน**อัลกอริทึม HS256 (HMAC-SHA256)** เพื่อป้องกันการดักแฮกข้อมูล (Data Tampering) และการนำคำสั่งเดิมมาส่งซ้ำ (Anti-Replay Attack) [cite: 56, 163]
*   ยิงคำขอทำรายการแบบ `POST` ไปที่เอนด์พอยต์ `{{API_ENDPOINT}}/api/v1/payout/create` พร้อมแนบ Header `x-api-key` [cite: 23].

#### **ขั้นตอนที่ 2: รูปแบบระบบอนุมัติคำสั่งซื้อ (Authorization Options)**
เมื่อเกตเวย์ได้รับข้อมูลธุรกรรม จะประมวลผลคำสั่งซื้อโดยอิงตามรูปแบบนโยบายระบบควบคุม 2 ประเภท [cite: 126, 173]:

*   **แบบที่ 1: Direct Auto-Payout (โอนเงินอัตโนมัติทันที - เหมาะสำหรับสตรีมเว็บเกม/เดิมพัน):**
    *   ไม่มีการแบ่งสิทธิ์ตรวจสอบด้วยมือ [cite: 173] เมื่อระบบ Gateway แกะ Signature คลายลายเซ็นตรวจสอบว่าถูกต้อง 100% [cite: 176] จะเปลี่ยนสถานะธุรกรรมเป็น **`pending`** [cite: 22, 153] จากนั้นนำคำสั่งสอดเข้าส่งต่อไปยังระบบ Banking API ของธนาคารปลายทางเพื่อประมวลผลทันทีในระดับวินาที [cite: 175, 178].
*   **แบบที่ 2: Dual Control / Four-Eye Principle (ระบบ 4 ตา / 2 ฝ่ายอนุมัติ - สำหรับความปลอดภัยระดับองค์กร):**
    *   **Maker (ผู้ป้อน/พนักงานบัญชี):** ล็อกอินด้วย User ของบัญชี บจก. ที่ผูกกับ Merchant (1 บัญชีมีได้หลาย User) แล้วสร้างรายการขอโอนออก รายการจะอยู่ในสถานะ Draft/Pending Approval ค้างอยู่ในคิวโดยที่**เงินยังไม่ถูกตัดออกจากบัญชีบริษัท** [cite: 128, 130].
    *   **Approver (ผู้อนุมัติ/ผู้บริหาร):** User อีกคนภายใต้บัญชี บจก. เดียวกันได้รับการแจ้งเตือน ล็อกอินเข้ามาตรวจสอบความเหมาะสม และทำการกรอกชุดตัวเลข OTP ยืนยันตัวตนชั้นที่สองจากอุปกรณ์ **Mobile Token** หรือ **Hardware Token (2FA)** เพื่อปล่อยวงเงินตัดยอดจริง [cite: 130, 142].
    *   **Inquiry:** User สิทธิ์ดูอย่างเดียวสำหรับกระทบยอด Statement ของบัญชี บจก. นั้น โดยไม่สร้างหรืออนุมัติรายการโอน

#### **ขั้นตอนที่ 3: กระบวนการส่งต่อและโอนฝั่งธนาคาร (Core Banking Processing)**
*   เมื่อยอดเงินถูกส่งเข้าทราฟฟิกหลักของธนาคาร สถานะจะเปลี่ยนจาก `pending` สู่ **`processing` (กำลังโอนกลางทาง)** [cite: 22, 153] เพื่อดึงเงินออกจากบัญชี Outbound บจก. ของเรา [cite: 175, 181] 
*   หากรายการถูกต้อง ครบถ้วนตามวงเงิน บัญชีปลายทางไม่ติดล็อก ยอดเงินจะส่งถึงลูกค้าสำเร็จ สถานะจะเปลี่ยนเป็น **`completed` (สำเร็จ)** [cite: 22, 153]
*   หากเลขบัญชีผิดพลาด หรือระบบธนาคารปลายทางติดขัดปิดปรับปรุง รายการจะเปลี่ยนสถานะเป็น **`failed` / `rejected` (ล้มเหลว)** พร้อมบันทึกข้อความระบุสาเหตุทางเทคนิคย้อนหลัง [cite: 22, 153, 164].

#### **ขั้นตอนที่ 4: การตอบรับแจ้งเตือนย้อนหลัง (Webhook Callback & Idempotency)**
*   ทันทีที่ระบบของธนาคารประมวลผลยอดเงินเสร็จสิ้น Gateway จะยิงข้อมูล **POST Webhook Callback** กลับมาอัปเดตเซิร์ฟเวอร์หลังบ้านของเราแบบเรียลไทม์ [cite: 22, 153]
*   **สเปกความปลอดภัยสูง:** ใน Webhook จะแนบค่า **`hash` (เข้ารหัส AES-256 จาก API Key + Secret Key)** และข้อมูลรูปภาพสลิปที่ออกจริงจากทางธนาคารกลับคืนมา เพื่อให้เซิร์ฟเวอร์ของเราคัดกรองว่าเป็นข้อมูลจริง และป้องกัน Fake Webhook [cite: 32, 156]
*   **การประมวลผลป้องกันรายการเบิ้ล (Idempotency):** เซิร์ฟเวอร์ฝั่งเราจะต้องตรวจสอบ `transactionId` ซ้ำในระบบทุกครั้ง หากตรวจพบว่าสถานะธุรกรรมดังกล่าวถูกอัปเดตเป็นเสร็จสมบูรณ์ไปก่อนหน้าแล้ว จะต้องทำการบันทึก Log และส่งตอบ HTTP Status `200 OK` ปิดเซสชันทันที ห้ามเติมยอดหรือหักคะแนนผู้ใช้ซ้ำซ้อน [cite: 153, 156].

### 4. การจัดการเชิงธุรกิจ: สภาพคล่องและการสำรองวงเงิน (Liquidity Management)

ในสถาปัตยกรรมระดับ SaaS Enterprise ที่มียอดคำขอถอนเงิน (Payout) สูงระดับวันละ 500,000 – 1,000,000+ บาทต่อหนึ่ง Tenant [cite: 148, 184] ระบบความปลอดภัยหลังบ้านจำเป็นต้องปฏิบัติตาม **นโยบายรักษาสภาพคล่องทางการโอน (Pre-funding Policy)** เพื่อไม่ให้รายการโอนออกสะดุด [cite: 148]:

*   **การคำนวณ Buffer Balance (ยอดเงินสำรองคงเหลือขั้นต่ำ):**
    *   **Minimum Critical Buffer (จุดวิกฤต - 10%):** จำกัดให้บัญชี Outbound ต้องมีเงินสดสำรองค้างไว้ไม่ต่ำกว่า 50,000 – 100,000 บาท [cite: 148] หากยอดเงินสดลดลงแตะระดับนี้ Gateway จะระงับคำขอ Payout เข้าคิวหน่วง (pending) ทันที เพื่อเลี่ยงการโอนล้มเหลวอันจะส่งผลต่อความเชื่อมั่นของแบรนด์ [cite: 148, 151].
    *   **Safety Working Float (จุดส่งพิกัดแจ้งเตือน - 20%-30%):** เมื่อเงินกองกลางเหลือประมาณ 150,000 – 300,000 บาท ระบบจะสั่งสั่นกระดิ่งแจ้งเตือน (Urgent Alert) ผ่านช่องทางต่างๆ เพื่อให้ฝ่ายการเงินของ Tenant เติมเงินเพิ่มเติม [cite: 148, 150].
*   **กลไก Auto-Sweep (การป้อนเงินอัตโนมัติ):** ตั้งรอบดึงข้อมูลระบบอัตโนมัติ ทุก ๆ 2 ชั่วโมงเพื่อกวาดเงินรับหน้าบ้าน (Inbound Account) เข้ามาพักและทบสมทบไว้ในบัญชีสั่งจ่ายโอนออก (Outbound Account) เพื่อลดต้นทุนความปลอดภัยของการหมุนเวียนเงินภายนอกอย่างมีประสิทธิภาพสูงสุดครับ [cite: 149, 150].
