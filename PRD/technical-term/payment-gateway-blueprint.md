# Blueprint สถาปัตยกรรมและการเชื่อมต่อระบบ Enterprise Payment Gateway (SaaS-Ready) - [Version 2]

เอกสารฉบับนี้จัดทำขึ้นเพื่อเป็นพิมพ์เขียว (Blueprint) ในการออกแบบ พัฒนา และเชื่อมต่อระบบรับชำระเงิน (Deposit) และระบบโอนเงินออก (Payout) เพื่อรองรับสถาปัตยกรรมแบบ **SaaS Enterprise Multi-Tenant** โดยปรับปรุงใหม่เพื่อให้สอดคล้องกับแผนงานการเชื่อมต่อโดยตรงกับระบบธนาคารกรุงไทยผ่าน **KTB Corporate Online API (บัญชี บจก. 10 หลัก)** เป็นช่องทางประมวลผลหลัก ร่วมกับระบบ **Dynamic QR Code (สุ่มเศษสตางค์)** เป็นระบบสำรองเพื่อความแม่นยำและปลอดภัยสูงสุดระดับองค์กร

---

## 1. คอนเซ็ปต์หลักและภาพรวม (Core Concept & Overview)

ระบบ Payment Gateway ในระดับ SaaS Enterprise ทำหน้าที่เป็นระบบหลังบ้านอัจฉริยะ (Middleware Layer) ที่คอยประสานงาน จัดการ และแปลงธุรกรรมทางการเงินให้เป็นอัตโนมัติทั้งหมด (Automated Financial Processing) ทั้งฝั่งขาเข้า (Inbound/Deposit) และขาออก (Outbound/Payout) โดยไม่ใช้แรงงานคนในการตรวจเช็ค (Zero Manual Matching)

### 🔑 แกนหลักในการทำระบบ: Automated Reconciliation (การกระทบยอดอัตโนมัติ)
โครงการนี้ปรับโครงสร้างการทำงานโดยกำหนดให้มีการประมวลผลและตรวจสอบยอดผ่าน 2 กลไกสำคัญ โดยสลับสัดส่วนความสำคัญเพื่อให้เอื้อต่อโปรเจกต์ระดับ Enterprise:

1. **Transfer Deposit (การจับคู่จากสเตทเมนต์ KTB Corporate API - ระบบการทำงานหลัก):**
   * **หลักการทำงาน:** ระบบโอนเงินโดยตรงผ่านธนาคาร (Bank Transfer) จะถูกตั้งเป็นวิธีการหลัก โดยอาศัยการเชื่อมต่อตรงแบบ Direct API กับธนาคารกรุงไทย (KTB Corporate Online) ของบัญชี บจก.
   * **กลไกการจับคู่:** ระบบจะสืบค้นและจับคู่ประมวลผลจากข้อมูลบัญชีธนาคารและชื่อบัญชีของผู้โอน (Sender Bank Account Number + Name) ที่ส่งและลงทะเบียนในระบบต้นทาง นำข้อมูลนี้มาตรวจสอบเทียบกับยอดเงินจริงและชื่อในสเตทเมนต์เงินเข้าที่ดึงมาแบบเรียลไทม์ ป้องกันปัญหาการใช้สลิปโอนเงินปลอมได้อย่างเด็ดขาด
2. **Dynamic QR Deposit (เศษสตางค์สุ่ม - ระบบสำรอง/ระบบทางเลือก):**
   * **หลักการทำงาน:** ใช้สำหรับการชำระเงินประเภท PromptPay QR Code ผ่านแอปพลิเคชันมือถือ
   * **กลไกการจับคู่:** มีการนำ "ยอดฝาก" มาบวก/ลบเศษสตางค์สุ่ม (Randomized Amount) อยู่ในช่วง **±1.99 บาท** (Unique Floating Amount) เช่น ตั้งใจโอน 100 บาท ระบบจะสุ่มเป็น 100.73 หรือ 99.58 บาท ซึ่งเศษสตางค์นี้จะมีอายุจำกัด (Timeout) และถือเป็นตัวระบุธุรกรรมตัวเดียวในระบบชำระเงินช่วงเวลานั้นๆ ทำให้ระบบจับคู่ออเดอร์ได้แม่นยำ 100%

## 2. ข้อมูลรับรองความปลอดภัยสำหรับ SaaS Multi-Tenant (Prerequisites)

เพื่อการต่อยอดระบบไปสู่ SaaS Enterprise ที่รอบรับลูกค้าได้หลายองค์กร (Multi-Tenant) ทุกธุรกรรมจะต้องถูกแยกด้วยระบบกุญแจความปลอดภัยและ Tenant Identifiers ทั้งหมด 4 ตัวแปรหลัก:

*   **API Key (`x-api-key`):** รหัสระบุตัวตนประจำแอปพลิเคชัน ส่งผ่าน Request Header เพื่อบอก Gateway ให้รู้ว่า Request นี้มาจาก Tenant ใด และมีสิทธิ์ใช้งาน API เอนด์พอยต์นี้หรือไม่
*   **Secret Key:** กุญแจลับระดับสูงสุดประจำแอปพลิเคชันหลังบ้าน **ห้ามเปิดเผยต่อสาธารณะเด็ดขาด** ใช้สำหรับเข้ารหัสสร้างและตรวจสอบลายเซ็นความปลอดภัย (Digital Signature) เท่านั้น
*   **Merchant ID:** รหัสประจำตัวร้านค้า/แพลตฟอร์ม (Tenant ID) ในระบบ เพื่อใช้จัดกลุ่มรายรับ ยอด Settlement และค่าธรรมเนียม — **1 Merchant มีได้หลายบัญชี บจก.** และแต่ละบัญชีมีได้หลาย User
*   **Client ID:** รหัสระบุตัวตนของไคลเอนต์ย่อยภายใต้ Merchant ที่เป็นผู้เริ่มต้นทำรายการธุรกรรมนั้นๆ

## 3. ระบบความปลอดภัยและการสร้างลายเซ็นดิจิทัล (Digital Signature - HS256)

สถาปัตยกรรมระดับ Enterprise กำหนดให้ทุก API Request ที่มีการสร้างธุรกรรม ย้ายเงิน หรือเข้าถึงข้อมูลสิทธิ์ จะต้องทำการแนบ **Digital Signature** เพื่อป้องกันการแฮกแก้ไขยอดเงิน (Data Tampering) และการสวมรอยทำธุรกรรมซ้ำ (Replay Attack)

### 3.1 วิธีการสร้าง Signature (Standard Signature Creation Steps)
1. **เตรียม Payload ตัวแปร:** กำหนดโครงสร้าง JSON ประกอบไปด้วยรหัสยืนยันตน ได้แก่ `merchantId`, `clientId` และเวลาปัจจุบันของระบบหลังบ้าน `timestamp` (ต้องมีค่าเป็นตัวเลขในหน่วย **มิลลิวินาที / Milliseconds** เพื่อความละเอียดและจำกัดอายุ Signature)
2. **ลงลายเซ็นความปลอดภัย (Signing):** นำ Payload และ `Secret Key` ของ Tenant มาประมวลผลเข้ารหัสผ่าน**อัลกอริทึม HS256 (HMAC-SHA256)** ซึ่งเป็นมาตรฐานสากลที่มีความเร็วสูง ปลอดภัย และรอบรับในทุกภาษาหลักหลังบ้าน (Node.js, Java, PHP, C#)
3. **กำหนดการใช้ครั้งเดียวทิ้ง (Single-Use Token Rule):** ค่า timestamp ที่ใช้สร้าง JWT (iat) จะต้องเป็น**ค่าเดียวกันถ้วนหน้า**กับพารามิเตอร์ `timestamp` ใน Request Body เมื่อ Gateway ได้รับคำขอ จะทำการตรวจสอบความถูกต้องของ Signature ถอดรหัส Timestamp ออกมาเทียบ และตรวจสอบเวลาจำกัด หากมีการส่งคำขอซ้ำด้วยลายเซ็นเดิม ระบบจะปฏิเสธ (Single-Use Rule)

### 3.2 รูปแบบ JSON Payload ตัวอย่างในการแนบ Signature
```json
{
  "clientId": "SaaS_CLIENT_001",
  "merchantId": "MERCHANT_ENTERPRISE_99",
  "signature": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJtZXJjaGFudElkIjoiU2FhU19N...",
  "timestamp": 1728319408897
}
```

## 4. แผนภาพและกระบวนการทำงานระดับ Enterprise (End-to-End Workflows)

### 4.1 วงจรระบบรับชำระเงิน (Deposit Flow / Inbound)

ระบบรับชำระเงินหลักถูกขยายเพื่อรองรับสถาปัตยกรรม Direct KTB Corporate API คู่ขนานไปกับ Dynamic QR Code:

```
[ ผู้ใช้งาน (Frontend) ]         [ ระบบ Backend (SaaS Core) ]          [ KTB / Gateway API ]
           │                                 │                                 │
           │ 1. เลือกโอนเงิน / ระบุข้อมูล     │                                 │
           ├────────────────────────────────►│ 2. บันทึกเลขบัญชี + ชื่อผู้โอน   │
           │                                 │                                 │
           │                                 │ 3. ตรวจสอบบัญชีด้วยระบบหลัก     │
           │                                 ├────── GET KTB Statement ───────►│ (ดึงประวัติเงินเข้า Real-time)
           │                                 │◄───── 200 OK (Statement Data) ──┤
           │                                 │                                 │
           │                                 │ 4. กรณีสำรอง: ยิงสร้าง QR สุ่ม    │
           │                                 ├────── POST /deposit/create ────►│
           │                                 │◄───── 200 OK (QR Payload / Ref) ┤ (สุ่มยอดเงิน ±1.99)
           │ 5. นำข้อมูลโอน / QR ไปสแกนจ่าย  │                                 │
           │◄────────────────────────────────┤                                 │
           │                                 │                                 │
     [ ลูกค้าสแกนชำระเงิน / โอน ]               │                                 │
           │                                 │                                 │
           ▼                                 │                                 │
     [ เครือข่ายธนาคาร ] ──────────────────────────────────────────────────────►│ (รับรายการเงินโอนเข้า บจก.)
                                             │                                 │
                                             │                                 │ 6. ดึงข้อมูลตรวจสอบ
                                             │ 7. ยิง Webhook / Auto-Reconciliation
                                             │◄───── POST callbackUrl ─────────┤ (สถานะ: completed / expired)
                                             ├────── HTTP 200 OK ─────────────►│
                                             │
                                             │ 8. ปลดล็อกคำสั่งซื้อ / เพิ่มยอด
           │◄────────────────────────────────┤
     [ ชำระเงินสำเร็จ ]
```

#### การบริหารจัดการสถานะรายการฝาก (Deposit Statuses Lifecycle):
*   **pending (เริ่มต้น):** รายการถูกสร้างในฐานข้อมูลเสร็จสิ้น หน้าต่างชำระเงินเตรียมรับข้อมูลและแสดงผลแก่ลูกค้า (สุ่มเศษสตางค์หากเป็น QR หรือล็อกเงื่อนไขบัญชีผู้โอนหากเป็นวิธีหลัก) และเริ่มนับถอยหลังหมดเวลา (Timeout อย่างน้อย 5 นาที)
*   **completed (สำเร็จ):** ลูกค้าโอนเงินเรียบร้อย ระบบตรวจสอบข้อมูลสำเร็จ:
    *   *ระบบหลัก (Transfer):* ตรวจพบเลขบัญชีและชื่อบัญชีผู้โอนจริงใน KTB Statement ตรงกับข้อมูลออเดอร์ที่จองไว้
    *   *ระบบสำรอง (QR):* ตรวจพบยอดเงินรวมเศษสตางค์สุ่มเข้ามาตรงตามเงื่อนไขก่อนหมดเวลา
*   **expired (หมดเวลา/ผิดพลาด):** ธุรกรรมไม่มียอดเงินเข้าตามกรอบเวลา, ลูกค้าเปลี่ยนยอดโอน (ปัดเศษทศนิยมสำหรับวิธี QR), หรือลูกค้าสแกนใช้ภาพ QR เก่าที่ล่วงอายุไปแล้ว

### 4.2 วงจรระบบจ่ายเงิน / โอนออก (Payout Flow / Outbound)

ระบบ Payout สำหรับนิติบุคคลและ SaaS Enterprise จะต้องไม่ถูกสั่งโอนออกโดยไม่มีการควบคุม เพื่อป้องกันความเสี่ยงทางการเงิน สถาปัตยกรรมจึงบังคับใช้หลักการ **Dual Control (Maker & Approver) แบบ 4 ตา (Four-Eye Principle)**:

```
[ Maker (พนักงานสร้างรายการ) ]       [ Approver (ผู้อนุมัติ) ]        [ SaaS Backend ]        [ Gateway API ]
              │                               │                      │                     │
       1. สร้างคำขอโอนเงิน                    │                      │                     │
       ───────────────────────────────────────┼─────────────────────►│ (Status: DRAFT)     │
                                              │                      │                     │
                                       2. ตรวจสอบ & กดยืนยัน (2FA/OTP)│                     │
                                       ─────────────────────────────►│ (Status: APPROVED)  │
                                                                     │                     │
                                                                     │ 3. Sign & ยิงคำขอ Payout
                                                                     ├────────────────────►│ POST /payout/create
                                                                     │◄── 200 OK (Pending) ┤
                                                                     │                     │
                                                                     │                     │ [ Bank Processes ]
                                                                     │ 4. Webhook Callback │
                                                                     │◄────────────────────┤ (COMPLETED / FAILED)
                                                                     ├────────────────────►│ (HTTP 200 OK)
```

1.  **Maker Role:** ผู้เตรียมธุรกรรม (เช่น พนักงานบัญชี) ล็อกอินด้วย User ของบัญชี บจก. ที่ระบุ — **1 บัญชี บจก. มีได้หลาย Maker** — สร้างรายการคำขอโอนเงินโดยกรอกเลขบัญชี จำนวนเงิน และรหัสธนาคารปลายทาง โดยที่ระบบจะทำการระงับยอดเงิน (Status: `pending`) แต่จะ**ยังไม่มีสิทธิ์สั่งจ่ายเงินออกจากบัญชี**
2.  **Approver Role:** เจ้าของบริษัท กรรมการ หรือผู้จัดการระดับสูง ล็อกอินด้วย User อีกชุดภายใต้บัญชี บจก. เดียวกันมาตรวจสอบข้อมูล ความถูกต้องของบัญชีผู้รับเงิน และต้องกรอกรหัส **OTP หรือ Mobile Token (2FA)** ผ่านอุปกรณ์ฮาร์ดแวร์/ซอฟต์แวร์ยืนยันตัวตนเพื่ออนุมัติ รายการจึงจะส่งตัดยอดจริง
3.  **Payout Status Lifecycle:**
    *   `pending` : คำสั่งจ่ายถูกสร้างและตรวจสอบสิทธิ์อนุมัติแล้ว อยู่ในคิวรอประมวลผล
    *   `processing` : Gateway ส่งคำสั่งให้ธนาคารดำเนินการตัดยอดและโอนเงินออก
    *   `completed` : เงินโอนเข้าบัญชีปลายทางเรียบร้อย Webhook ยิงตอบกลับแจ้งพร้อมสลิป (QR) จากฝั่งธนาคาร
    *   `failed` / `rejected` : การโอนล้มเหลวเนื่องจากข้อมูลบัญชีผิดพลาด หรือระบบธนาคารปลายทางปิดปรับปรุง

## 5. กลไกตรวจสอบข้อมูลระดับสูง (Advanced Webhook & Verification)

### 5.1 Webhook Anti-Spoofing & AES Encryption
เพื่อความปลอดภัยระดับสูงสุด ป้องกันไม่ให้แฮกเกอร์แอบยิง Webhook ข้อมูลชำระเงินปลอมมาที่เซิร์ฟเวอร์ของเรา (Fake Callback Webhook) เพื่อรับเครดิตฟรี ในเพย์โหลดของ Webhook จะต้องแนบพารามิเตอร์รหัสลับมาด้วย:
*   **hash:** เป็นชุดข้อมูลเข้ารหัสที่ปลอดภัยสูงสุด โดยใช้**การเข้ารหัส AES (Advanced Encryption Standard)**
*   **วิธีการเข้ารหัสคีย์:** ระบบจะนำตัวแปร `transactionId` มาเข้ารหัสด้วยคีย์ลับเฉพาะที่สร้างขึ้นจากการต่อสายอักขระร่วมกันของ **`API_KEY` และ `SECRET_KEY` ของ Tenant**
*   **ฝั่งรับ Webhook หลังบ้านของเรา:** จะต้องนำค่าดังกล่าวมาทำกระบวนการ Decrypt หากถอดรหัสออกมาแล้วได้ค่า `transactionId` ตรงตามที่ธนาคารส่งมาจริง จึงจะอนุมัติธุรกรรม

### 5.2 กลไก Idempotency Handling (ป้องกันธุรกรรมซ้ำซ้อน)
เนื่องจากเครือข่ายอินเทอร์เน็ตอาจเกิดปัญหาคอขวด ทำให้ระบบธนาคารหรือ Gateway ทำการ Retry Webhook ซ้ำเข้ามาหาเซิร์ฟเวอร์ของเราหลายครั้ง ระบบหลังบ้านฝั่งผู้รับ Webhook จะต้องปฏิบัติตามหลัก **Idempotency** อย่างเคร่งครัด:
1. เมื่อเซิร์ฟเวอร์ได้รับ Webhook เข้ามา ให้เช็คสถานะ `transactionId` ในฐานข้อมูลทันที
2. หากธุรกรรมถูกเปลี่ยนสถานะเป็น `completed` ไปแล้ว ระบบจะต้องไม่ประมวลผลการเติมเงิน/ปลดล็อคซ้ำอีกเป็นครั้งที่สองเพื่อป้องกันช่องโหว่ทางบัญชี
3. ระบบจะทำการบันทึก Log การทำซ้ำ และต้องส่งคืนสถานะผลลัพธ์ **HTTP 200 OK** กลับไปยังธนาคารเสมอ เพื่อจบการทำงานอย่างราบรื่น

## 6. แนวทางสถาปัตยกรรมต่อยอดสู่ระบบ SaaS Enterprise Platform

เมื่อต้องการสเกลระบบเพื่อรองรับลูกค้าจำนวนมาก (Tenants) ในรูปแบบแพลตฟอร์มการเงินแบบบริการส่วนกลาง (SaaS Multi-tenant Payment Service) คุณจำเป็นต้องพัฒนาโมดูลพิเศษเพิ่ม 3 ส่วน:

1.  **Multi-Tenant Gateway Layer (Key Vault):**
    ออกแบบระบบเก็บข้อมูลความปลอดภัย (Credentials) อย่างแยกส่วน โดยห้ามฮาร์ดโค้ดรหัสเด็ดขาด ให้ใช้โซลูชัน เช่น HashiCorp Vault เพื่อเก็บบรรจุและเรียกใช้ `Secret Key`, `API Key` และ `Merchant ID` ของ Tenant แต่ละรายแยกจากกันอย่างปลอดภัยและเป็นระเบียบ
2.  **Event-Driven & Asynchronous Message Queue:**
    หลีกเลี่ยงการเขียนสคริปต์ให้ทำงานหนักขณะรับ Webhook (Response Time สำหรับ Webhook จะต้องต่ำกว่า **2 วินาที**) ทันทีที่เซิร์ฟเวอร์ได้รับ Webhook เข้ามา ตรวจเช็ค Header เบื้องต้นเสร็จแล้ว ให้บันทึก Log และตอบกลับ HTTP 200 OK ทันที จากนั้นนำรายการธุรกรรมนั้นโยนลงสู่คิวข้อความ (เช่น Redis Queue, RabbitMQ, Kafka) เพื่อให้ Worker หลังบ้านทำงานประมวลผลจับคู่ยอด (Auto-Match Worker) และอัปเดตสเตทเมนต์แบบ Asynchronous
3.  **Enterprise Financial Ledger & Audit Trail:**
    ทุกคำสั่งเปลี่ยนสถานะของเงินเข้าออก (State Machine) จะต้องบันทึกประวัติ Raw Payload ไว้อย่างครบถ้วนพร้อมเวลาลงทะเบียน และจัดทำงบบัญชีกระทบยอดประจำวัน (Daily Statement Reconciliation) เพื่อจัดแจงตรวจสอบและตรวจสอบย้อนกลับ (Audit) ได้ตลอดเวลา
