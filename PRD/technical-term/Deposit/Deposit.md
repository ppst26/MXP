จากการแกะสเปกคู่มือระบบ API ของ **FLASH-PAY** และ **BIT-PAYZ** ร่วมกับกลไกการเชื่อมต่อตรงกับธนาคารกรุงไทยผ่าน **KTB Corporate Online API** สำหรับโปรเจกต์ Enterprise SaaS ของคุณ [cite: 108, 109, 223, 236] ต่อไปนี้เป็นคำอธิบายเจาะลึกของ **ระบบฝากเงิน (Deposit Module)** โดยทำการ**แกะและวิเคราะห์โฟลว์การทำงาน (Workflows)** จากโครงสร้างแผนภาพในระบบอย่างละเอียดที่สุดครับ [cite: 119, 243]:

### 1. การวิเคราะห์โฟลว์ระบบฝากเงินแบบที่ 1: Dynamic QR Deposit (เศษสตางค์สุ่ม)

เป็นระบบทางเลือกหรือระบบสำรองที่มีประสิทธิภาพสูงมากในฝั่งหน้าบ้านสำหรับการสแกนจ่ายทันใจ โดยสลายขั้นตอนแชร์หน้าสลิปทิ้ง 100% [cite: 120, 236]

#### **กราฟิกแสดงวงจรการทำงาน (Dynamic QR Sequence Flow):** [cite: 238, 255]

```
[ ผู้ใช้งาน (Frontend) ]         [ ระบบ Backend (SaaS Core) ]          [ Payment Gateway API ]
           │                                 │                                 │
           │ 1. ขอชำระเงิน (ระบุยอด 500)      │                                 │
           ├────────────────────────────────►│ 2. สร้าง Signature (HS256)       │ [cite: 177, 257]
           │                                 │ 3. ส่งคำขอสร้างรายการชำระเงิน      │ [cite: 178, 257]
           │                                 ├────── POST /deposit/create ────►│ [cite: 171, 257]
           │                                 │                                 │ (สุ่มยอดเงิน ±1.99) [cite: 120, 257]
           │                                 │◄───── 200 OK (QR Payload / Ref) ┤ (สถานะ: pending) [cite: 120, 257]
           │ 4. นำ QR Payload ไป Render QR   │                                 │ [cite: 173, 257]
           │◄────────────────────────────────┤                                 │
           │                                 │                                 │
     [ ลูกค้าสแกนชำระเงิน 500.35 บาท ]           │                                 │
           │                                 │                                 │
           ▼                                 │                                 │
     [ เครือข่ายธนาคาร ] ──────────────────────────────────────────────────────►│ (รับ Statement เงินเข้า) [cite: 256, 257]
                                             │                                 │
                                             │                                 │ 5. Gateway ทำ Auto-Match ยอดเศษ
                                             │ 6. ยิง Webhook แจ้งเตือนสถานะ   │ [cite: 121, 257]
                                             │◄───── POST callbackUrl ─────────┤ (สถานะ: completed) [cite: 120, 257]
                                             ├────── HTTP 200 OK ─────────────►│ [cite: 257, 258]
                                             │
                                             │ 7. ปรับยอดเครดิตในเกมทันที
           │◄────────────────────────────────┤ [cite: 257]
     [ เครดิตอัปเดตเรียบร้อย ]
```

#### **แกะขั้นตอนการทำงานละเอียด (QR Flow Step-by-Step):**

1.  **Initiate Request:** ลูกค้าร้องขอฝากเงินยอด 500 บาทจากหน้าเบราว์เซอร์ [cite: 256, 257].
2.  **Signature Generation:** ระบบ Backend ของเราคำนวณรหัสลายเซ็น JWT ด้วยกุญแจลับ `Secret Key` ผ่านอัลกอริทึม **HS256** ผูกกับมิลลิวินาทีของเวลาขณะนั้น [cite: 111, 241].
3.  **POST Create Deposit:** ระบบของเราส่งข้อมูลไปที่เอนด์พอยต์ `POST /api/v1/deposit/create` โดยส่งพารามิเตอร์ประเภทรายการเป็น **`type: "QR"`** พร้อมระบุยอดเงินที่ต้องการฝาก [cite: 171, 257].
4.  **Amount Randomization:** ระบบ Gateway ประมวลผลและ**สุ่มเศษสตางค์ในช่วง ±1.99 บาท** (เช่น ยอด 500 บาท สุ่มออกมาเป็น **500.35 บาท**) [cite: 120, 256] โดยตั้งสถานะธุรกรรมเป็น **`pending`** เพื่อรอเงินเข้า และส่งรหัส QR Payload (`qrcode`) พร้อมกับวันเวลาหมดอายุ (`expireDate`) กลับมาให้เรา [cite: 120, 153, 256].
5.  **Render & Checkout:** ระบบหลังบ้านของเรารับข้อมูลมา จากนั้นส่งรหัส QR Payload String ไปให้ฝั่ง Frontend ทำการแปลงเป็นรูปภาพ QR Code ด้วย Library หน้าบ้าน เพื่อให้ลูกค้าใช้แอปพลิเคชันธนาคารสแกนชำระเงิน **500.35 บาท** โดยระบุข้อความแจ้งเตือนห้ามปัดเศษหรือแก้ไขยอดเด็ดขาด [cite: 120, 173].
6.  **Auto-Reconciliation:** เมื่อลูกค้าโอนเงินเข้าบัญชี บจก. ของเรา ระบบของ Gateway จะดึงข้อมูลรายการเคลื่อนไหวทางบัญชี (Statement) แล้วดักจับยอดเงินโอนที่มีเศษสตางค์ตรงกับยอดที่สุ่มไว้ (500.35 บาท) ภายในช่วงเวลาที่กำหนด [cite: 120, 256].
7.  **Webhook Trigger:** เมื่อจับคู่สำเร็จ Gateway จะปรับสถานะรายการเป็น **`completed`** แล้วทำการ**ยิง Webhook Callback (HTTP POST)** กลับมายังระบบเรา เพื่อทำการเติมเครดิตในบัญชีผู้ใช้ทันทีแบบอัตโนมัติ [cite: 120, 121, 256].

### 2. การวิเคราะห์โฟลว์ระบบฝากเงินแบบที่ 2: Transfer Deposit (จับคู่จากสเตทเมนต์ - ระบบหลัก)

เป็นระบบการทำงานหลักของแพลตฟอร์ม SaaS Enterprise ของคุณ เพื่อรับมือกับธุรกรรมโอนเงินแบบบัญชีสู่บัญชีตรง [cite: 243]. โดยใช้สถาปัตยกรรมสืบค้นยอดเงินจริงจาก Statement API ของบัญชี บจก. KTB Corporate มากระทบยอดโดยตรงตามพารามิเตอร์บัญชีผู้โอนต้นทาง [cite: 11, 12].

#### **กราฟิกแสดงวงจรการทำงาน (Transfer Deposit Matching Engine):** [cite: 243]

```
[ ลูกค้ากรอกเลขบัญชีต้นทางที่ใช้โอน ] ──► [ ตรวจสอบชื่อ บช. (POST /bank/verify/bankAccountName) ] [cite: 117, 243]
                                              │
                                              ▼
[ สร้างรายการฝาก (Status: pending) ] ◄── [ Backend บันทึก RefID + บัญชีผู้โอนลง DB ] [cite: 120, 243]
                                              │
                                   ( ลูกค้าสลับไปแอปธนาคารเพื่อโอนเงิน )
                                              │
                                              ▼
[ KTB Corporate Direct API ] ──► [ สืบค้น Statement / รายการเงินเข้า Real-time ] [cite: 11, 12]
                                              │
                                              ▼
                        [ Matching Engine หลังบ้านเริ่มประมวลผล 3 เงื่อนไข ] [cite: 243]
                        1. เลขที่บัญชีผู้โอนตรงกัน (bankAccountNumber) [cite: 120, 243]
                        2. ยอดเงินตรงตามรายการ (amount) [cite: 120, 243]
                        3. อยู่ในกรอบเวลา Timeout (timestamp) [cite: 120, 243]
                                              │
                       ┌──────────────────────┴──────────────────────┐
                       ▼                                             ▼
             [ ข้อมูลตรงตามเงื่อนไขครบถ้วน ]                [ ข้อมูลไม่ตรง หรือ หมดเวลา ] [cite: 243]
                       │                                             │
             [ ปรับสถานะ: completed ]                      [ ปรับสถานะ: expired / failed ] [cite: 120, 243]
                       │                                             │
             [ ส่ง Webhook Callback ปลุกออเดอร์ ]           [ ส่ง Webhook แจ้งเตือนหมดเวลา ] [cite: 121, 243]
```

#### **แกะขั้นตอนการทำงานละเอียด (Transfer Matching Flow):**

1.  **Pre-Validation:** ลูกค้าระบุเลขบัญชีธนาคารต้นทางและชื่อของตนเองลงบนระบบหน้าเว็บก่อนทำการโอน, ระบบของเราจะยิงคำขอไปที่ `POST /api/v1/client/bank/verify/bankAccountName` เพื่อตรวจสอบและจดจำรูปแบบชื่อนามสกุลผู้โอนล่วงหน้าจากฐานข้อมูลธนาคาร [cite: 117, 243].
2.  **Create Deposit:** ระบบยิงคำขอสร้างรายการฝากไปที่ Gateway โดยระบุ **`type: "TRANSFER"`** พร้อมแนบข้อมูลเลขบัญชีธนาคารต้นทางผู้โอน โดยในระบบ TRANSFER นี้**ไม่จำเป็นต้องส่งยอดเงินล่วงหน้า (Amount is not required)** [cite: 120, 171]. ธุรกรรมจะถูกตั้งค่าค้างในสถานะ **`pending`** [cite: 120].
3.  **Statement Polling:** ลูกค้าเปิดแอปพลิเคชันธนาคารเพื่อทำการโอนเงินเข้าบัญชี บจก. KTB ของระบบเราแบบปกติ, ระบบหลังบ้านของเราจะทำงานร่วมกับ KTB API ในการคอยดึงข้อมูลความเคลื่อนไหวทางบัญชี (Statement Transaction Data) ล่าสุดแบบ Real-time [cite: 11, 12].
4.  **Matching Engine Engine:** อัลกอริทึมหลังบ้านทำการแกะและตรวจสอบข้อมูลเปรียบเทียบ 3 ปัจจัยร่วม [cite: 243]:
    - **เลขบัญชีต้นทางผู้โอน:** ตรงกับที่ลูกค้าลงทะเบียนไว้ล่วงหน้าหรือไม่? [cite: 243, 244]
    - **ยอดเงินโอน:** ยอดเงินสุทธิใน स्टेटमेंट ตรงกับยอดคำสั่งซื้อที่ขอเข้ามาหรือไม่? [cite: 244]
    - **วันเวลา:** ธุรกรรมเงินโอนเข้าเกิดขึ้นในกรอบเวลาก่อนหมดอายุ (`timeout`) ที่ระบุไว้หรือไม่? [cite: 244]
5.  **State Transition:** เมื่อตรวจพบข้อมูลตรงครบทุกเงื่อนไข ระบบจะเปลี่ยนสถานะจาก `pending` สู่ **`completed`** ทันที และส่งยิง Webhook แนบรหัสและประวัติสลิปแจ้งไปยังระบบเว็บหลักเพื่ออัปเดตผลชำระเงิน [cite: 120, 121, 243, 244].

  "transactionId": "BZP0PTB01776723e7X1", // บังคับ - ไอดีเลขธุรกรรมเฉพาะที่ระบบเราเจนขึ้น [cite: 171]

### 4. โครงสร้าง Webhook Callback ที่ส่งกลับมายังเซิร์ฟเวอร์ของเรา (Webhook Specifications)

เมื่อสถานะธุรกรรมสิ้นสุดลงที่ `completed` หรือ `expired` ระบบจะยิงข้อมูลมาที่ URL ที่ระบุไว้ใน `callbackUrl` โดยแยกโครงสร้างพอร์ตข้อมูลตามประเภทดังนี้ [cite: 120, 121]:

#### **ฝั่ง Dynamic QR Deposit (Webhook Payload):** [cite: 128]

ระบบจะส่งค่า **`hash`** ซึ่งเป็นผลลัพธ์การเข้ารหัส AES-256 ของตัวแปร `transactionId` โดยใช้คีย์ความลับที่เกิดจากการเชื่อมต่อรหัส **`API_KEY + SECRET_KEY`** เข้าด้วยกัน เพื่อให้เซิร์ฟเวอร์เราใช้ Decrypt ยืนยันความปลอดภัย ต้าน Webhook ปลอม [cite: 127, 128]:

```json
{
  "referenceId": "w5EIFM4i1M", // ไอดีอ้างอิงจากระบบ Gateway [cite: 128]
  "transactionId": "BZP0PTB01776723e7X1", // ไอดีธุรกรรมจากระบบเรา [cite: 128]
  "clientId": "nHUxQbHgEu",
  "merchantId": "VOBM7qzaRH",
  "walletId": "WALLET_SAAS_01",
  "bankCode": "014",
  "bankName": "SCB",
  "bankAccountNumber": "1714436599",
  "bankAccountName": "ปิยรัฐ แก้วจันทร์",
  "amount": 100.73, // ยอดโอนจริงที่รวมเศษสตางค์แล้ว [cite: 128]
  "status": "completed", // สถานะของธุรกรรม ("completed" หรือ "expired") [cite: 128]
  "timestamp": 1728329638,
  "matchTimestamp": 1728329640826, // เวลาที่ระบบสืบค้นเจอข้อมูลเงินตรงกัน [cite: 128]
  "type": "QR",
  "hash": "U2FsdGVkX1/Z6EHf3XX6hmzlnK7TvYoLKsUlyR0F47LIERkRq2fKKhKwpwq3j9wu" // ตัวดักจับความปลอดภัย [cite: 128]
}
```

ข้อมูลจะถูกส่งกลับมาในคีย์อาเรย์ย่อยชื่อ **`newTransactions`** ซึ่งเป็นโครงสร้างชุดข้อความดิบส่งตรงจากบันทึก Statement ของธนาคาร โดยจะมีค่า `checkStr` เพื่อเป็นตัวแปรตรวจสอบเงื่อนไขความถูกต้องของงบบัญชี [cite: 125]:
